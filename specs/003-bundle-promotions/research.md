## 1. แยก aggregate ใหม่ ไม่ขยาย `Promotion` เดิม

**Decision**: สร้าง `ConditionalPromotion` เป็น aggregate root ใหม่ มีตารางของตัวเอง repository ของตัวเอง
และ controller ของตัวเองที่ `/api/v1/conditional-promotions` โดย **ไม่แตะ `Promotion.cs`, `PromotionConfiguration.cs`,
`PromotionRepository.cs`, `PromotionsController.cs` และตาราง `promotions` เลย**

**Rationale**: FR-026 กำหนดว่าโปรโมชั่นเปอร์เซ็นต์เดิมต้องทำงานเหมือนเดิมทุกประการ และ Assumptions ระบุว่า
ไม่ย้ายข้อมูลเดิม การแยกแบบนี้ทำให้ข้อกำหนดนั้น **ตรวจสอบได้ด้วยการดู git diff** ว่าไฟล์เดิมไม่ถูกแตะ
ไม่ต้องอาศัยการรันเทสอย่างเดียว นอกจากนี้รูปร่างข้อมูลสองแบบต่างกันมาก (ของเดิมเป็น flat row ตัวเดียว
ของใหม่มี collection ของรายการเงื่อนไข) การบีบให้อยู่ตารางเดียวกันจะทำให้คอลัมน์ nullable งอกขึ้นเยอะโดยไม่จำเป็น

**Alternatives considered**:
- *Table-per-hierarchy (TPH) บน `Promotion` เดิม พร้อมคอลัมน์ discriminator* — ต้องแก้ `Promotion.cs`
  ซึ่งมี invariant ที่บังคับว่า `DiscountPercentage` ต้องอยู่ในช่วง (0,100] เสมอ แต่โปรโมชั่นแบบของแถมไม่มีเปอร์เซ็นต์
  จึงต้องผ่อน invariant เดิมลง = เปลี่ยนพฤติกรรมของเดิม ขัด FR-026 โดยตรง และต้องเขียน migration ที่แตะข้อมูลเดิม
- *ยัดเงื่อนไขเป็น JSON column ใน `promotions`* — ทำให้ query "โปรโมชั่นไหนอ้างถึงสินค้าที่ถูกลบ" (FR-023)
  กลายเป็นการอ่านทุกแถวมา deserialize ในหน่วยความจำ และ EF Core จะ track การเปลี่ยนแปลงไม่ได้ตามปกติ

## 2. `CartPricer` เป็น domain service แบบ pure function ตัวเดียวที่ตั้งราคาตะกร้า

**Decision**: ตรรกะการตั้งราคาตะกร้าทั้งหมด (นับชุด จัดสรรสินค้า คิดส่วนลดชุด ส่วนลดรายชิ้นของเศษ
ส่วนลดระดับบิล และแบ่งบรรทัดของแถม) อยู่ใน `CartPricer` ตัวเดียว รับพารามิเตอร์เข้าครบ
คืน `PricedCart` ออกมา **ไม่เรียก repository ไม่อ่านนาฬิกาเอง ไม่แตะ I/O ใดๆ**

พารามิเตอร์ที่รับเข้า:
1. **รายการตะกร้าที่รวมยอดตาม `productId` แล้ว** (`productId` + จำนวน)
2. **ตารางค้นหาสินค้า** (`productId` → ชื่อ + ราคา) ที่ครอบคลุม **สินค้าในตะกร้า ∪ สินค้าทุกตัวที่โปรโมชั่น
   ผู้เข้าชิงอ้างถึง** — ไม่ใช่แค่สินค้าในตะกร้า ดูเหตุผลที่ข้อ #7
3. โปรโมชั่นเปอร์เซ็นต์ที่มีผล (`Promotion[]`)
4. โปรโมชั่นแบบมีเงื่อนไขที่มีผลและใช้ได้ (`ConditionalPromotion[]`)
5. มีสมาชิกผูกกับบิลหรือไม่ (bool) และวันที่ (`DateOnly`)

`DiscountResolver` เดิมไม่ถูกแก้ `CartPricer` เรียกใช้ต่อสำหรับส่วนลดรายชิ้นของหน่วยที่เหลือและส่วนลดระดับบิล

**Rationale**: constitution Principle III บังคับว่า business logic ต้องเทสได้โดยไม่พึ่ง PostgreSQL —
pure function ทำให้เทสทุก acceptance scenario เป็นการเรียกฟังก์ชันตรงๆ พร้อมตัวเลขที่คาดหวัง
และที่สำคัญกว่านั้นคือ FR-012/SC-006 ต้องการให้พรีวิวกับ checkout ให้ผลเท่ากันเป๊ะ — วิธีเดียวที่รับประกันได้
คือให้ทั้งสองเส้นทางเรียกโค้ดก้อนเดียวกัน ไม่ใช่โค้ดสองก้อนที่ตั้งใจให้เหมือนกัน

**Alternatives considered**:
- *ขยาย `DiscountResolver` เดิม* — `DiscountResolver` มีสัญญาแบบ "รับฐานเงินมา คืนจำนวนส่วนลด" ซึ่งใช้กับ
  โปรโมชั่นแบบชุดไม่ได้ เพราะแบบชุดต้อง**จัดสรรหน่วยสินค้า**ข้ามหลายรายการ ไม่ใช่คิดเปอร์เซ็นต์จากก้อนเดียว
  การยัดเข้าไปจะทำให้ signature เดิมเปลี่ยนและกระทบ FR-026
- *ให้ `CompleteSaleUseCase` คำนวณเอง* — use case อยู่ใน Application layer และถือ repository อยู่แล้ว
  จะทำให้เทสต้อง mock repository เพื่อเทสเลขคณิต และพรีวิวจะต้อง copy ตรรกะไปอีกที่

## 3. `POST /api/v1/sales/preview` — endpoint ใหม่สำหรับพรีวิวตะกร้า

**Decision**: เพิ่ม `POST /api/v1/sales/preview` บน `SalesController` รับ request body รูปร่างเดียวกับ checkout
คืน `PricedCart` เต็มรูปแบบ (บรรทัดที่แยกแล้ว ของแถม สิทธิ์ที่ถูกใช้ สิทธิ์ที่ยังไม่ได้ใช้ ยอดรวม)
**ไม่เปิด transaction ไม่ตัดสต็อก ไม่บันทึกอะไรลงฐานข้อมูล**

สิทธิ์: `SalesController` ไม่มี `[Authorize(Roles=...)]` ระดับคลาส และ `Program.cs:87` ตั้ง `FallbackPolicy`
เป็น `RequireAuthenticatedUser()` ดังนั้น endpoint นี้จึงเรียกได้ทั้งแคชเชียร์และผู้จัดการโดยอัตโนมัติ
ซึ่งเป็นสิ่งที่ต้องการ — ต่างจาก `PromotionsController` ที่เป็น Manager-only จึงใช้เป็นแหล่งข้อมูลของหน้าขายไม่ได้

**Rationale**: constitution Principle I ประโยคที่สองระบุว่าข้อมูลทุกอย่างที่ frontend ต้องใช้ ต้องมาจาก
versioned REST endpoint หน้าขายต้องแสดงส่วนลดชุดและข้อความเตือนสิทธิ์ที่ยังไม่ได้ใช้ก่อนกดชำระเงิน (FR-013, FR-015)
ถ้าไม่มี endpoint นี้ ทางเลือกเดียวที่เหลือคือ `web/` คำนวณเอง ซึ่งละเมิดทั้ง Principle I และ Principle III
(ตรรกะหลุดออกจาก domain layer ที่มีเทส) และจะทำให้ยอดพรีวิวกับยอดจริงเพี้ยนกันได้

**Alternatives considered**:
- *ให้หน้าขายดึงรายการโปรโมชั่นมาแล้วคำนวณฝั่ง client* — ละเมิด constitution ตามข้างบน และแคชเชียร์
  ไม่มีสิทธิ์เรียก `/api/v1/promotions` อยู่แล้ว
- *ใส่พรีวิวเป็น query string บน `GET /api/v1/sales`* — ตะกร้าเป็น payload ที่มีโครงสร้าง ยัดใส่ query string
  ไม่เหมาะและชนกับ endpoint ประวัติการขายที่มีอยู่
- *ให้ `POST /api/v1/sales` รับ flag `dryRun`* — ทำให้ endpoint เดียวมีสองพฤติกรรมที่ต่างกันมาก
  (อันหนึ่งตัดสต็อก อันหนึ่งไม่) เสี่ยงต่อการส่ง flag ผิดแล้วขายจริงโดยไม่ตั้งใจ

## 4. ของแถมเป็น `SaleLineItem` แยกบรรทัด พร้อม flag `IsGift`

**Decision**: ของแถมบันทึกเป็น `SaleLineItem` คนละบรรทัดกับสินค้าที่จ่ายเงินเสมอ แม้เป็นสินค้ารายการเดียวกัน
โดย `UnitPriceSnapshot` = ราคาปกติ, `Quantity` = จำนวนที่แถม, `DiscountAmount` = ราคาปกติ × จำนวนที่แถม
(ยอดสุทธิ = 0) และเพิ่มคอลัมน์ `IsGift` (boolean, default false) บน `SaleLineItem`

**Rationale**: FR-016 กำหนดว่าใบเสร็จต้องแสดงราคาปกติไม่ใช่ 0 บาท ซึ่งรูปแบบนี้ให้พอดี และยังเข้ากันได้กับ
invariant เดิมของ `SaleLineItem` ทุกข้อโดยไม่ต้องแก้ constructor (`UnitPriceSnapshot > 0` ✓,
`Quantity > 0` ✓, `DiscountAmount >= 0` ✓) — ถ้าเลือกเก็บของแถมเป็นบรรทัดราคา 0 จะชน invariant
`UnitPriceSnapshot > 0` ทันทีและต้องผ่อนกฎเดิมลง

เหตุผลที่ต้องมี flag `IsGift` แยกต่างหาก: **ส่วนลดชุด 100% ก็ทำให้ยอดสุทธิเป็น 0 เหมือนกัน**
ใบเสร็จจึงแยก "ของแถม" ออกจาก "ลด 100%" ด้วยตัวเลขอย่างเดียวไม่ได้ ต้องมีข้อมูลบอกตรงๆ

**Alternatives considered**:
- *อนุมานว่าเป็นของแถมเมื่อ `DiscountAmount == UnitPrice × Quantity`* — ผิดในกรณีส่วนลดชุด 100%
  ตามที่อธิบายข้างบน และผิดถ้าในอนาคตมีส่วนลดรายชิ้น 100%
- *ตารางแยกสำหรับของแถม* — ทำให้ `Sale.SubtotalAmount`/`DiscountAmount`/`TotalAmount` ที่คำนวณจาก
  `_lineItems` อย่างเดียวต้องเปลี่ยนสูตร กระทบรายงานและใบเสร็จเดิมทั้งหมดโดยไม่ได้อะไรเพิ่ม

## 5. ส่วนลดระดับบิลไม่นับของแถมทั้งในฐานและในการกระจาย

**Decision**: `CartPricer` คำนวณฐานส่วนลดระดับบิลจาก **ผลรวมของบรรทัดที่ลูกค้าจ่ายเงินเท่านั้น**
และกระจายส่วนลดระดับบิลลงเฉพาะบรรทัดที่จ่ายเงิน บรรทัดของแถมไม่ได้รับส่วนแบ่งใดๆ
ส่วนบรรทัดที่ได้ส่วนลดชุดแบบเปอร์เซ็นต์ยังนับเข้าฐานที่ราคาเต็มตามปกติ

**Rationale**: FR-021 กำหนดตรงๆ ว่ามูลค่าของแถมต้องไม่เป็นฐานของส่วนลดระดับบิล
และในทางเทคนิค ถ้าบรรทัดของแถม (ยอดสุทธิ 0 อยู่แล้ว) ได้รับส่วนแบ่งส่วนลดระดับบิลเพิ่ม ยอดสุทธิของบรรทัดนั้น
จะติดลบ ทำให้ invariant `SubtotalAmount - DiscountAmount == TotalAmount` ยังเป็นจริงแต่ใบเสร็จอ่านไม่รู้เรื่อง
ส่วนการให้บรรทัดส่วนลดชุดยังนับเข้าฐานที่ราคาเต็ม เป็นพฤติกรรมเดียวกับส่วนลดรายชิ้นแบบเดิมทุกประการ
และตรงกับตัวเลขที่ spec ยืนยันไว้ที่ User Story 3 scenario 4 (ส่วนลดบิล 15 บาท = 5% ของ 300 ไม่ใช่ 5% ของ 255)

**Alternatives considered**:
- *คิดฐานจากยอดสุทธิหลังหักส่วนลดรายการ* — เปลี่ยนพฤติกรรมของโปรโมชั่นระดับบิลเดิม ขัด FR-026
  และทำให้ตัวเลขใน US3 scenario 4 ไม่ตรงกับ spec

## 6. `SaleAppliedPromotion` บันทึกสิทธิ์ที่ถูกใช้แนบกับบิล

**Decision**: เพิ่ม owned collection `AppliedPromotions` บน `Sale` แต่ละแถวเก็บ `PromotionId` (ไม่มี FK),
`DescriptionSnapshot` (ข้อความบรรยายโปรโมชั่น ณ เวลาที่ขาย), `SetCount`, `DiscountAmount`
`Sale` constructor รับ collection นี้เข้ามาพร้อม line items — บิลยังเป็น append-only ไม่มี mutation API เพิ่ม

ข้อความบรรยายถูกประกอบที่ฝั่ง server (`ConditionalPromotion` มี method สร้างข้อความของตัวเอง) และ
endpoint รายการโปรโมชั่นก็คืนข้อความเดียวกันนี้ เพื่อให้ `web/` ไม่ต้องประกอบข้อความเอง (FR-008)

**Rationale**: FR-024 กำหนดว่าประวัติการขายและใบเสร็จต้องอธิบายที่มาของส่วนลดได้ **แม้โปรโมชั่นจะถูกแก้ไข
หรือลบไปแล้ว** จึงต้องเก็บเป็น snapshot ไม่ใช่ join กลับไปที่ตารางโปรโมชั่น ซึ่งเป็นรูปแบบเดียวกับที่
`SaleLineItem` เก็บ `ProductNameSnapshot`/`UnitPriceSnapshot` อยู่แล้วในระบบนี้ — สอดคล้องกับของเดิม

## 7. ไม่ตั้ง foreign key ไปที่ `products` — กรองด้วยการตรวจการมีอยู่แทน

**Decision**: `ConditionLine.ProductId` และ `Reward.GiftProductId` **ไม่มี** FK constraint ไปที่ตาราง `products`
(ตรงกับ `Promotion.ProductId` เดิมที่ `PromotionConfiguration` ก็ไม่ได้ตั้ง FK ไว้)
แทนที่จะพึ่ง FK ให้ use case **โหลดสินค้าทุกตัวที่เกี่ยวข้องมาในคำสั่งเดียว** คือ
*สินค้าในตะกร้า ∪ สินค้าทุกตัวที่โปรโมชั่นแบบมีเงื่อนไขที่มีผลอ้างถึง* (ได้ทั้ง id, ชื่อ, ราคา และรู้ว่าตัวไหนหายไป)
แล้วตัดโปรโมชั่นที่มีสินค้าหายไปแม้แต่ตัวเดียวออกจากการพิจารณา **ก่อน** ส่งที่เหลือเข้า `CartPricer`
พร้อมส่งตารางค้นหาสินค้าก้อนเดียวกันนี้เข้าไปด้วย

**ทำไมต้องโหลดสินค้าที่ไม่ได้อยู่ในตะกร้าด้วย**: `CartPricer` ต้องใช้ **ราคา** ของสินค้าที่แถมเพื่อจัดลำดับ
โปรโมชั่นตามมูลค่าส่วนลดต่อชุด (ข้อ #9) และต้องใช้ **ชื่อ** ของสินค้าที่แถมเพื่อสร้างข้อความเตือนสิทธิ์
ที่ยังไม่ได้ใช้ (FR-015) — ในสถานการณ์หลักของ User Story 1 ("ซื้อ A+B แถม C" โดยยังไม่ได้สแกน C)
สินค้า C ยังไม่อยู่ในตะกร้า ถ้าโหลดแค่สินค้าในตะกร้า ทั้งสองอย่างนี้จะคำนวณไม่ได้เลย

endpoint รายการโปรโมชั่นทำการตรวจแบบเดียวกันเพื่อคืนฟิลด์ `isUsable` และ `unusableReason` (FR-023)

**Rationale**: ถ้าตั้ง FK แบบ `RESTRICT` จะทำให้ลบสินค้าที่ถูกอ้างถึงไม่ได้ = เปลี่ยนพฤติกรรมการลบสินค้าของ 001
ถ้าตั้งเป็น `CASCADE` จะทำให้โปรโมชั่นหายเงียบๆ โดยผู้จัดการไม่รู้ตัว ซึ่งขัดกับ FR-023 ที่ต้องการให้
**แสดงสถานะว่าใช้ไม่ได้พร้อมเหตุผล** เพื่อให้ผู้จัดการตัดสินใจเอง

เหตุผลที่ต้องกรองก่อนเข้า `CartPricer` ไม่ใช่กรองทีหลัง: FR-015 บอกให้ระบบเตือนว่า "ยังไม่ได้ใช้สิทธิ์แถม X"
ถ้าไม่กรองก่อน ระบบจะขึ้นเตือนให้แคชเชียร์ไปหยิบสินค้าที่ถูกลบไปแล้วและเพิ่มเข้าตะกร้าไม่ได้ — เตือนแล้วแก้ไม่ได้

---

## 8. สลับลำดับใน `CompleteSaleUseCase`: ตั้งราคาก่อน ตัดสต็อกทีหลัง

**Decision**: เปลี่ยนลำดับใน `CompleteSaleUseCase` จากเดิม (วนทีละบรรทัด → ตัดสต็อกทันที → คิดส่วนลด)
เป็น: โหลดสินค้าทุกตัวในตะกร้า → เรียก `CartPricer` → ตัดสต็อกตามจำนวนรวมของทุกบรรทัด **รวมจำนวนของแถม** →
สร้าง `Sale` → อัปเดตยอดสะสมสมาชิก → commit ทั้งหมดอยู่ใน transaction เดิมเหมือนเดิม

`InsufficientStockException` ยังถูกโยนด้วย signature เดิม เพียงแต่เกิดขึ้นช้ากว่าเดิมในลำดับการทำงาน

**Rationale**: จำนวนของแถมเป็นผลลัพธ์ของการตั้งราคา (ขึ้นกับจำนวนชุดที่ได้) จึงรู้จำนวนที่ต้องตัดสต็อกจริง
ไม่ได้จนกว่าจะตั้งราคาเสร็จ การตัดสต็อกก่อนตั้งราคาแบบโค้ดปัจจุบันจึงเป็นไปไม่ได้อีกต่อไป
เขียนข้อนี้ไว้ชัดเจนเพราะเป็นการแก้ลำดับที่มองข้ามง่ายและจะทำให้ FR-017 ตกหล่นเงียบๆ

**หมายเหตุ**: ในทางปฏิบัติจำนวนของแถมจะไม่เกินจำนวนที่แคชเชียร์สแกนเข้าตะกร้าอยู่แล้ว (FR-014 บังคับว่า
ระบบไม่เพิ่มสินค้าเอง) การตัดสต็อกจึงเป็นจำนวนเดียวกับที่ผู้ใช้ขอมา แต่การเขียนลำดับให้ถูกยังจำเป็น
เพราะ `CartPricer` เป็นตัวตัดสินว่าบรรทัดถูกแบ่งอย่างไร

## 9. ลำดับการจัดสรรที่กำหนดได้ (FR-019) ต้องเป็น total order

**Decision**: เรียงโปรโมชั่นแบบมีเงื่อนไขด้วยกุญแจสามชั้น: **มูลค่าส่วนลดต่อหนึ่งชุด มาก→น้อย**,
แล้ว **`StartDate` เก่า→ใหม่**, แล้ว **`Id` น้อย→มาก**

มูลค่าส่วนลดต่อชุดคำนวณดังนี้:
- สิ่งตอบแทนแบบของแถม = จำนวนที่แถม × ราคาปัจจุบันของสินค้าที่แถม
- สิ่งตอบแทนแบบเปอร์เซ็นต์ = เปอร์เซ็นต์ × ผลรวมของ (จำนวนขั้นต่ำ × ราคาปัจจุบัน) ของทุกรายการในเงื่อนไข

**Rationale**: FR-019 ระบุแค่สองชั้นแรก แต่สองชั้นนั้นยัง**ไม่เป็น total order** — โปรโมชั่นสองตัวที่ให้ส่วนลด
ต่อชุดเท่ากันและเริ่มวันเดียวกันจะยังเสมอกัน ทำให้ผลลัพธ์ขึ้นกับลำดับที่ฐานข้อมูลคืนแถวมา ซึ่งละเมิด FR-012
และ SC-006 ที่บังคับว่าตะกร้าเดียวกันต้องได้ยอดเท่ากันทุกครั้ง การเพิ่ม `Id` เป็นชั้นสุดท้ายปิดช่องนี้
โดยไม่ขัดกับ FR-019 (เป็นการขยายกฎให้ครบ ไม่ใช่เปลี่ยนกฎ)

**Alternatives considered**:
- *หาชุดค่าผสมที่ให้ส่วนลดรวมสูงสุด* — เป็นปัญหา combinatorial optimization ผู้ทดสอบคำนวณตามมือไม่ได้
  และเวลาตอบลูกค้าหน้าร้านว่า "ทำไมบิลนี้ได้เท่านี้" จะอธิบายไม่ได้ spec จึงเลือก greedy ที่อธิบายได้แทน
- *เรียงตามวันที่สร้างอย่างเดียว* — ไม่ให้ประโยชน์สูงสุดแก่ลูกค้าในกรณีที่โปรโมชั่นดีกว่ามาทีหลัง

## 10. อัลกอริทึมตั้งราคาตะกร้า (สัญญาของ `CartPricer`)

เขียนเป็นขั้นตอนมีเลขกำกับ เพื่อให้ `/speckit-tasks` และคนเขียนโค้ดไม่ต้องคิดใหม่

1. **รวมยอดตะกร้าตาม `productId`** แล้วเรียงตาม `productId` — request ปัจจุบันไม่ได้รวมรายการซ้ำ
   ถ้าส่ง A มาสองบรรทัดโดยไม่รวมก่อน จะกลายเป็นการจัดสรรสองรอบอิสระและได้ของแถมเกินจริง
2. **กรองโปรโมชั่นแบบมีเงื่อนไข** เอาเฉพาะที่ (ก) มีผลในวันนั้น (ข) ผ่านเงื่อนไขสมาชิก
   (ค) สินค้าทุกตัวที่อ้างถึงยังมีอยู่จริง (ข้อ #7)
3. **เรียงตามกุญแจสามชั้น** ของข้อ #9
4. **วนทีละโปรโมชั่นตามลำดับ** โดยมีตัวนับ "จำนวนคงเหลือต่อสินค้า" ที่ลดลงเรื่อยๆ:
   - จำนวนที่ใช้ต่อชุดของสินค้าแต่ละรายการในเงื่อนไข = `จำนวนขั้นต่ำ` และ **บวกจำนวนที่แถมเข้าไปด้วย
     ถ้าสินค้าที่แถมเป็นรายการเดียวกัน** (FR-011)
   - `sets` = ค่าน้อยที่สุดของ `floor(คงเหลือ[สินค้า] ÷ จำนวนที่ใช้ต่อชุด)` ข้ามทุกรายการในเงื่อนไข (FR-010)
   - ถ้า `sets == 0` ข้ามโปรโมชั่นนี้
   - หักจำนวนที่ใช้ออกจากคงเหลือของทุกรายการในเงื่อนไข (FR-018: หน่วยที่ถูกใช้แล้วห้ามถูกนับซ้ำ)
   - **ถ้าสิ่งตอบแทนเป็นของแถมและสินค้าที่แถมไม่ได้อยู่ในเงื่อนไข**:
     `giftApplied = min(sets × จำนวนที่แถม, คงเหลือ[สินค้าที่แถม])` แล้วหักออกจากคงเหลือ
     ส่วนที่ขาด (`sets × จำนวนที่แถม − giftApplied`) บันทึกเป็น "สิทธิ์ที่ยังไม่ได้ใช้" สำหรับ FR-015
     — **จำนวนชุดต้องไม่ถูกจำกัดด้วยการมีของแถมในตะกร้าหรือไม่** เพราะ FR-015 ต้องการให้เตือนได้ว่าขาดกี่ชิ้น
   - **ถ้าสิ่งตอบแทนเป็นของแถมและสินค้าที่แถมอยู่ในเงื่อนไขด้วย**: จำนวนที่แถม = `sets × จำนวนที่แถม`
     ซึ่งถูกหักออกไปแล้วในขั้นตอนหักคงเหลือ ไม่ต้องหักซ้ำ และไม่มีสิทธิ์ที่ยังไม่ได้ใช้ในกรณีนี้
   - **ถ้าสิ่งตอบแทนเป็นเปอร์เซ็นต์**: ส่วนลดของสินค้าแต่ละรายการในเงื่อนไข =
     `round(เปอร์เซ็นต์ ÷ 100 × จำนวนขั้นต่ำ × sets × ราคา, 2)` (FR-020 — เฉพาะจำนวนที่ครบชุด)
   - บันทึก `SaleAppliedPromotion` (โปรโมชั่น, ข้อความบรรยาย, `sets`, ส่วนลดรวม)
5. **หน่วยที่เหลือของแต่ละสินค้า** (ไม่ถูกใช้ในชุดใดเลย) → `DiscountResolver.ResolveItemDiscount`
   ตามกติกาเดิม "ใช้ส่วนลดที่มากที่สุดเพียงแบบเดียว" (FR-018 ประโยคท้าย, `001/FR-022`)
6. **ประกอบบรรทัด** ต่อสินค้าหนึ่งรายการ:
   - บรรทัดที่จ่ายเงิน: `Quantity` = จำนวนในตะกร้า − จำนวนที่แถม,
     `DiscountAmount` = ส่วนลดชุดแบบเปอร์เซ็นต์ + ส่วนลดรายชิ้นของหน่วยที่เหลือ, `IsGift` = false
   - บรรทัดของแถม (สร้างเมื่อจำนวนที่แถม > 0): `Quantity` = จำนวนที่แถม,
     `DiscountAmount` = ราคา × จำนวนที่แถม, `IsGift` = true
   - ถ้าจำนวนที่จ่ายเงินเป็น 0 (แถมล้วน) ให้ไม่สร้างบรรทัดที่จ่ายเงิน
7. **ส่วนลดระดับบิล**: ฐาน = ผลรวม `ราคา × จำนวน` ของบรรทัดที่จ่ายเงินเท่านั้น →
   `DiscountResolver.ResolveBillDiscount` → กระจายลงบรรทัดที่จ่ายเงินตามสัดส่วน
   โดยยกเศษจากการปัดไปไว้บรรทัดสุดท้าย (ตรรกะเดิมของ `DistributeBillDiscount` แค่เปลี่ยนชุดบรรทัดที่รับการกระจาย)

### ตรวจอัลกอริทึมด้วยมือกับตัวเลขใน spec

| กรณี | ตะกร้า | ผลตามอัลกอริทึม | ตรงกับ spec |
|---|---|---|---|
| US1 sc3 — "ซื้อ A1+B1 แถม C1" | A 3, B 2, C 3 | sets = min(3,2) = 2; C แถม 2 เหลือ C จ่าย 1 | ✓ |
| US2 sc2 — "ซื้อ A2 แถม A1" | A 5 | ใช้ต่อชุด = 2+1 = 3; sets = floor(5/3) = 1; แถม 1 จ่าย 4 = 400 | ✓ |
| US2 sc3 | A 6 | sets = 2; แถม 2 จ่าย 4 = 400 | ✓ |
| US2 sc4 | A 2 | sets = floor(2/3) = 0; จ่ายเต็ม 200 | ✓ |
| US2 sc5 — มีลดรายชิ้น 10% ด้วย | A 5 | sets = 1 (ใช้ 3 หน่วย); เหลือ 2 หน่วยได้ 10%; (4×100−20) + (1×100−100) = 380 | ✓ |
| US3 sc1 — "ซื้อ A1+B1 ลด 15%" | A1 B1 D1 | 15%×100 + 15%×200 = 45; D เต็ม 50 | ✓ |
| US3 sc4 — บวกลดทั้งบิล 5% | A1 B1 | ฐานบิล = 300 → 15; รวมจ่าย 300−45−15 = 240 | ✓ |
| Edge — "ซื้อ A1+B1 แถม A1" | A 3, B 1 | ใช้ต่อชุดของ A = 1+1 = 2; sets = min(floor(3/2), 1) = 1; A จ่าย 2 แถม 1; B จ่าย 1 | ✓ |

## 11. รูปแบบข้อความบรรยายโปรโมชั่น (FR-008) ประกอบที่ฝั่ง server

**Decision**: `ConditionalPromotion` มี method ประกอบข้อความบรรยายของตัวเองในรูปแบบ
`ซื้อ {ชื่อสินค้า} {จำนวน} [+ {ชื่อสินค้า} {จำนวน}]... {แถม {ชื่อสินค้า} {จำนวน} | ลด {x}%}`
โดยรับชื่อสินค้าเข้ามาเป็นพารามิเตอร์ (domain layer ไม่ควรไปดึงชื่อสินค้าเอง)
ข้อความนี้ถูกใช้ทั้งในรายการโปรโมชั่น (FR-008) และเป็น `DescriptionSnapshot` ตอนขาย (FR-024)

**Rationale**: ถ้าปล่อยให้ `web/` ประกอบข้อความเอง ข้อความในหน้าจัดการโปรโมชั่นกับข้อความบนใบเสร็จจะเพี้ยนกันได้
และเมื่อบันทึกเป็น snapshot ต้องใช้ข้อความรูปแบบเดียวกันอยู่แล้ว การมีจุดประกอบเดียวจึงถูกกว่า
