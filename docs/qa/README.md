# คู่มือ: สั่ง AI ให้สร้างเทสต์ที่ครอบคลุม

คู่มือชุดนี้สอนวิธี **ใช้ AI agent (Claude Code) สร้างและดูแลชุดทดสอบ** ของโปรเจกต์ TaladPOS
ตั้งแต่สั่งให้อ่าน codebase จนถึงสั่งรันทั้งหมดก่อน deploy

**ผู้อ่าน**: นักเรียน/นักพัฒนาที่พอเขียนโค้ดได้ แต่ยังไม่เคยใช้ AI agent ทำงาน QA อย่างเป็นระบบ
**ไม่ต้องรู้มาก่อน**: Playwright, xUnit, หรือ TaladPOS

---

## บทเรียนเดียวที่สำคัญที่สุด

> **เทสต์ต้องยืนยัน "สิ่งที่ spec บอกว่าควรเป็น" ไม่ใช่ "สิ่งที่โค้ดทำอยู่ตอนนี้"**

ถ้าคุณสั่งว่า *"เขียนเทสต์ให้ไฟล์ Cart.tsx"* — AI จะอ่านโค้ด เห็นว่ามันแสดงยอดรวมแบบหนึ่ง แล้วเขียนเทสต์
ยืนยันว่า "มันแสดงแบบนั้น" ผลคือ **เทสต์เขียวทุกครั้ง และไม่มีวันจับบั๊กได้เลย** เพราะมันแค่ถ่ายรูปโค้ดปัจจุบันไว้

ถ้าคุณสั่งว่า *"เขียนเทสต์ตาม FR-006 ใน spec.md"* — AI จะอ่านข้อกำหนดที่ว่า *"ต้องแสดงยอดรวมย่อย
ส่วนลด และยอดสุทธิ แบบเรียลไทม์"* แล้วเขียนเทสต์ที่ **แดง** เพราะโค้ดจริงแสดงแค่ยอดรวมย่อย

เทสต์ที่แดงตัวนั้นมีค่ามากกว่าเทสต์เขียว 50 ตัวที่ไม่ได้ตรวจอะไรเลย

คู่มือทุกบทวนกลับมาที่หลักข้อนี้

## สิ่งที่ต้องมีก่อนเริ่ม

| อย่าง | ตรวจด้วยคำสั่ง | ถ้าไม่มี |
|---|---|---|
| .NET SDK 8 | `dotnet --version` | ติดตั้งจาก dotnet.microsoft.com |
| Node.js 18+ | `node --version` | ติดตั้งจาก nodejs.org |
| Docker (สำหรับ PostgreSQL) | `docker --version` | ติดตั้ง Docker Desktop |
| PostgreSQL รันอยู่ | `docker compose up -d postgres` | รันคำสั่งซ้าย |
| Claude Code | `claude --version` | ดู claude.com/claude-code |

ตรวจว่าพร้อมจริงด้วยการรันชุดเทสต์ที่มีอยู่:

```bash
cd api && dotnet test TaladPOS.sln
```

ควรได้ผลประมาณนี้ (ตัวเลขอาจเพิ่มขึ้นตามเวลา):

```
Passed!  - Failed: 0, Passed: 45, Skipped: 0, Total: 45 - TaladPOS.Domain.Tests.dll
Passed!  - Failed: 0, Passed: 39, Skipped: 0, Total: 39 - TaladPOS.Application.Tests.dll
Passed!  - Failed: 0, Passed:  9, Skipped: 0, Total:  9 - TaladPOS.Api.IntegrationTests.dll
```

ถ้าชั้นที่สาม (IntegrationTests) แดง แปลว่า PostgreSQL ยังไม่พร้อม — กลับไปรัน `docker compose up -d postgres`

## ปิรามิดเทสต์ของโปรเจกต์นี้

โปรเจกต์นี้แบ่งเทสต์เป็น 4 ชั้น แต่ละชั้นตอบคำถามคนละแบบ **ห้ามสั่ง AI ให้เขียนเทสต์โดยไม่ระบุว่าชั้นไหน**

```
        ┌─────────────────────────────┐
        │  4. UI / E2E (Playwright)   │  ช้าสุด · เปราะสุด · ใกล้ผู้ใช้จริงสุด
        │     "แคชเชียร์กดปุ่มแล้วขายได้ไหม"    │  ← ยังไม่มีในโปรเจกต์
        ├─────────────────────────────┤
        │  3. API Integration (xUnit) │  ต้องใช้ PostgreSQL จริง
        │     "ยิง POST /sales แล้วได้ 201 ไหม" │  ← มี 9 เทสต์
        ├─────────────────────────────┤
        │  2. Application (xUnit)     │  ใช้ fake ไม่ต้องมี DB
        │     "use case เรียงลำดับงานถูกไหม"    │  ← มี 39 เทสต์
        ├─────────────────────────────┤
        │  1. Domain (xUnit)          │  เร็วสุด · เสถียรสุด
        │     "กติกาธุรกิจถูกไหม"              │  ← มี 45 เทสต์
        └─────────────────────────────┘
```

**กฎเหล็กจาก constitution ของโปรเจกต์** (`.specify/memory/constitution.md` ข้อ III — ระบุว่า NON-NEGOTIABLE):

> ชั้น 1 และ 2 **ต้องรันได้โดยไม่ต้องมี PostgreSQL และไม่ต้องต่อเน็ต** — ใช้ fake/mock ที่ขอบ infrastructure

ถ้าคุณสั่ง AI ว่า *"เขียน unit test ให้ CompleteSaleUseCase"* แล้วมันสร้างเทสต์ที่ต่อ database จริง
**นั่นคือผลลัพธ์ที่ผิด** ต้องสั่งใหม่ให้ใช้ fake repository แทน ไม่งั้นชุดเทสต์จะช้าและพังเป็นระยะ

## เอกสารอ้างอิงของโปรเจกต์

AI จะเขียนเทสต์ได้ดีก็ต่อเมื่อคุณชี้ให้มันอ่านของถูก:

| ไฟล์ | บอกอะไร | ใช้ตอนไหน |
|---|---|---|
| `specs/001-single-store-pos/spec.md` | ข้อกำหนด FR-001…FR-037, SC-001…SC-010 | **สำคัญที่สุด** — เป็นตัวตัดสินว่าเทสต์ควร assert อะไร |
| `specs/001-single-store-pos/contracts/*.md` | รูปแบบ request/response + status code ของทุก endpoint | เขียนเทสต์ชั้น 3 |
| `specs/001-single-store-pos/test-plan.md` | แผนเทสต์ 265 เคส พร้อม ID และ FR trace | เป็นแหล่งอ้างอิงหลักของคู่มือทุกบท |
| `specs/001-single-store-pos/data-model.md` | โครงสร้างข้อมูลและ invariant | เขียนเทสต์ชั้น 1 |
| `.specify/memory/constitution.md` | กฎที่ห้ามฝ่าฝืน | ตรวจว่าเทสต์ที่ AI เขียนไม่ผิดกฎ |

## ⚠️ สถานะปัจจุบันของโปรเจกต์ (อ่านก่อน อย่าให้เข้าใจผิด)

คู่มือนี้เขียนขณะที่โปรเจกต์อยู่ในสถานะนี้:

- **ชั้น 1–3 มีจริง รันได้จริงวันนี้** — `dotnet test` ใช้ได้เลย ตัวเลข 45/39/9 ข้างบนคือผลรันจริง
- **ชั้น 4 (UI/E2E) ยังไม่มี** — `web/package.json` ไม่มี Playwright, Vitest หรือ Jest เลยสักตัว
  และทั้งโปรเจกต์ยังไม่มี `data-testid` แม้แต่จุดเดียว

ดังนั้นในคู่มือ ทุกตัวอย่างจะติดป้ายบอกชัดว่าเป็นอย่างไหน:

| ป้าย | ความหมาย |
|---|---|
| ✅ **ผลจริง** | รันจริง/เกิดขึ้นจริงแล้ว คัดลอกผลมาตรง ๆ |
| 🔮 **รูปแบบที่คาด** | ยังไม่ได้ทำ — แสดงโครงผลลัพธ์ให้ดูว่าควรออกมาหน้าตาแบบไหน |

บทที่ 2 มีหัวข้อ *"สั่งให้ AI ติดตั้ง Playwright ให้"* ซึ่ง**เป็นบทเรียนโดยตั้งใจ** ไม่ใช่ขั้นตอนที่ข้ามได้ —
การสั่ง AI ตั้งค่าเครื่องมือทดสอบเป็นทักษะหนึ่งที่ต้องฝึก

## ข้อควรระวังที่ต้องบอกนักเรียนตั้งแต่วันแรก

1. **ห้ามให้ AI ลบหรือแก้เทสต์แดงเพื่อให้เขียว** — ถ้าเทสต์แดงเพราะโค้ดผิด ต้องแก้โค้ด
   ถ้าแดงเพราะ spec ยังไม่ชัด ให้ mark `Skip`/`fixme` พร้อมเขียนเหตุผลกำกับ **ห้ามลบทิ้งเงียบ ๆ**
2. **AI มั่นใจได้แม้ตอนที่ผิด** — ทุกบทมีหัวข้อ "วิธีตรวจว่าผลลัพธ์ดีจริง" ให้ใช้ทุกครั้ง อย่าเชื่อคำสรุปของ AI
3. **เทสต์ที่รันแล้วเขียวตั้งแต่ครั้งแรกเสมอ น่าสงสัย** — ลองแก้โค้ดให้พังโดยตั้งใจ ถ้าเทสต์ยังเขียว แปลว่ามันไม่ได้ตรวจอะไร
