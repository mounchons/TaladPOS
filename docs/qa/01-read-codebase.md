# บทที่ 1 — สั่ง AI อ่าน codebase เพื่อวางแผนเทสต์

## เป้าหมาย

ให้ AI สำรวจโค้ดและข้อกำหนด แล้วผลิต **แผนเทสต์ที่คุณตรวจทานได้ก่อนเขียนโค้ดจริง**
ห้ามข้ามขั้นนี้ไปสั่งเขียนเทสต์เลย เพราะคุณจะไม่มีทางรู้ว่ามันครอบคลุมหรือตกอะไร

---

## ทำไมต้องขอ "แผน" ก่อน ไม่ใช่ "เทสต์" เลย

ถ้าสั่งเขียนเทสต์ทันที คุณจะได้ไฟล์เทสต์ 20 ไฟล์ที่อ่านตรวจไม่ไหว และไม่รู้ว่ามันตก FR ข้อไหนไปบ้าง

แผนเทสต์คือ **สัญญา** ระหว่างคุณกับ AI ว่าจะทดสอบอะไรบ้าง มันสั้นพอจะอ่านทั้งหมดได้ใน 15 นาที
แก้ได้ง่าย และเมื่อตกลงกันแล้ว การเขียนโค้ดจึงเป็นแค่การแปลแผนเป็นโค้ด

---

## Prompt อ่อน vs Prompt ดี

### ❌ แบบอ่อน

```
เขียน unit test ให้โปรเจกต์นี้หน่อย
```

**จะได้อะไร**: AI สุ่มเปิดไฟล์ 2–3 ไฟล์ที่มันเจอก่อน แล้วเขียนเทสต์ให้ฟังก์ชันที่เห็น
โดยไม่รู้ว่าโปรเจกต์นี้มีข้อกำหนด 37 ข้อ ผลคือเทสต์กระจัดกระจาย ทับซ้อนของเดิม และตกเรื่องสำคัญ

---

### ❌ แบบอ่อน (ที่ดูเหมือนดีแล้ว แต่ยังไม่ใช่)

```
อ่านโค้ดใน web/src/components/Cart.tsx แล้วเขียนเทสต์ให้ครอบคลุม
```

**จะได้อะไร**: AI อ่านโค้ด เห็นว่า `Cart` คำนวณ `subtotal` แล้วแสดงผล → เขียนเทสต์ว่า
*"เมื่อใส่สินค้า 2 ชิ้นราคา 45 บาท ต้องแสดง 90.00"* → **เขียวทันที**

ปัญหาคือ FR-006 ใน `spec.md` กำหนดว่าต้องแสดง **ยอดรวมย่อย + ส่วนลด + ยอดสุทธิ** ครบสามค่า
แต่โค้ดจริงแสดงแค่ค่าแรก AI ไม่รู้เรื่องนี้เพราะคุณไม่ได้ให้มันอ่าน spec

**เทสต์ที่ได้จึงล็อกช่องว่างเอาไว้ แทนที่จะเปิดโปงมัน** — นี่คือกับดักที่พบบ่อยที่สุดในการใช้ AI เขียนเทสต์

---

### ✅ แบบดี

```
อ่าน codebase ทั้งโปรเจกต์ (api/ และ web/) พร้อมกับ specs/001-single-store-pos/spec.md
และ contracts/*.md

แล้วสร้างแผนเทสต์ที่ครอบคลุมการทำงานทั้งระบบ รวมถึงการทดสอบ CRUD ผ่าน UI ทุกหน้าจอ

ข้อกำหนดของแผน:
1. สำรวจก่อนว่าตอนนี้มีเทสต์อะไรอยู่แล้วบ้าง จะได้ไม่เขียนซ้ำ
2. ทุกเคสต้องอ้างอิงกลับไปที่ FR-xxx หรือ SC-xxx ใน spec.md
3. หน้าจอไหนไม่มี CRUD ครบ 4 อย่าง ให้ใส่ N/A พร้อมบอกเหตุผลจากสเปก
   ห้ามข้ามเงียบ ๆ
4. ถ้าเจอจุดที่โค้ดกับสเปกไม่ตรงกัน ให้แยกเป็นหัวข้อต่างหาก อย่าเพิ่งตัดสินว่าใครถูก
5. เขียนเป็นไฟล์ specs/001-single-store-pos/test-plan.md

ยังไม่ต้องเขียนโค้ดเทสต์ ทำแผนมาให้ตรวจก่อน
```

**ทำไมถึงดี** — แต่ละบรรทัดปิดช่องโหว่คนละอย่าง:

| บรรทัด | ปิดช่องโหว่อะไร |
|---|---|
| ให้อ่าน `spec.md` + `contracts/` | AI จะ assert ตามข้อกำหนด ไม่ใช่ตามโค้ดปัจจุบัน ← **สำคัญที่สุด** |
| ข้อ 1 สำรวจของเดิม | ไม่เขียนทับ 93 เทสต์ที่มีอยู่ |
| ข้อ 2 อ้าง FR | ตรวจย้อนได้ว่า FR ข้อไหนยังไม่มีเทสต์ |
| ข้อ 3 N/A พร้อมเหตุผล | แยก "ไม่มีฟีเจอร์" ออกจาก "ลืมทดสอบ" |
| ข้อ 4 แยกจุดที่ขัดกัน | AI ไม่แอบตัดสินใจแทนคุณ |
| "ยังไม่ต้องเขียนโค้ด" | หยุดให้ตรวจก่อน ไม่งั้นมันจะทำยาว 2 ชั่วโมงแล้วผิดทาง |

## ผลที่คาดว่าจะได้

✅ **ผลจริง** — prompt ข้างบนคือสิ่งที่ใช้จริงกับโปรเจกต์นี้ ผลลัพธ์คือไฟล์
[`specs/001-single-store-pos/test-plan.md`](../../specs/001-single-store-pos/test-plan.md) ที่มีอยู่จริงในโปรเจกต์แล้ว

AI ทำงานประมาณ 15–20 นาที (อ่านไฟล์ราว 30 ไฟล์) แล้วส่งไฟล์ที่มีโครงนี้:

```
§0  ขอบเขตและกติกา          ← อะไรอยู่ในเทสต์ อะไรไม่อยู่
§1  สถานะปัจจุบัน            ← มีเทสต์อะไรแล้ว ขาดอะไร
§2  เมทริกซ์ CRUD ทุกหน้าจอ   ← ตอบคำถาม "ครบทุกหน้าจอไหม"
§3  Domain      23 เคส
§4  Application 29 เคส
§5  API         89 เคส
§6  UI          111 เคส      ← แยกตามหน้าจอ
§7  Non-functional 13 เคส
§8  สิ่งที่ต้องตัดสินใจก่อน    ← AI ถามกลับ ไม่เดาเอง
§9  จุดที่โค้ดกับสเปกไม่ตรงกัน
§10 ลำดับทำงาน + คำสั่งรัน
```

รวม **265 เคส** — มีอยู่แล้ว 47 · ต้องเขียนใหม่ 218

แต่ละแถวหน้าตาแบบนี้:

| ID | เคส | FR | คาดหวัง | สถานะ | P |
|---|---|---|---|---|---|
| TC-UI-STOCK-013 | **D**: กด "ลบ" | FR-015 | แถวหายจากตาราง (⚠️ ไม่มีกล่องยืนยัน — ดู R-02) | ใหม่ | P1 |

---

## จุดที่พิสูจน์ว่า prompt ดีได้ผลจริง

ในการรันจริง AI พบเรื่องที่ **การอ่านโค้ดอย่างเดียวไม่มีวันเจอ** เพราะต้องเทียบกับสเปก:

> **R-01** — ตะกร้าแสดงแค่ "ยอดรวม" ที่เป็น subtotal (`web/src/components/Cart.tsx:222`)
> ไม่มีบรรทัดส่วนลดและยอดสุทธิก่อนกดชำระเงิน
> แต่ FR-006 เขียนว่า *"ต้องคำนวณและแสดงยอดรวมย่อย ส่วนลดที่เกี่ยวข้อง และยอดรวมสุทธิ แบบเรียลไทม์"*
> → เป็นบั๊กหรือจะปรับสเปก?

และอีกข้อที่เจอจากการเทียบ contract กับโค้ด:

> **R-08** — `contracts/sales.md` เขียนว่า 409 คืน `{"error":"insufficient_stock","productId":…}` (แบน)
> แต่โค้ดจริงส่ง `{"error":"insufficient_stock","details":{"productId":…}}` (ซ้อน)
> → ต้องชี้ว่าฝั่งไหนคือฉบับจริง ก่อนเขียนเทสต์

**นี่คือคุณค่าที่แท้จริงของขั้นตอนนี้** — ยังไม่ได้เขียนเทสต์สักบรรทัด แต่เจอปัญหาจริงไปแล้ว 8 ข้อ

---

## วิธีตรวจว่าแผนที่ได้ดีจริง

อ่านแผนที่ AI ส่งมา แล้วเช็กทีละข้อ ถ้าข้อไหนไม่ผ่าน ให้สั่งแก้ก่อนไปบทถัดไป

- [ ] **ทุกแถวมี FR หรือ SC อ้างอิง** — แถวที่ไม่มี แปลว่า AI คิดขึ้นเองจากโค้ด ให้ถามว่ามาจากไหน
- [ ] **สุ่มหยิบ FR มา 5 ข้อ แล้วหาในแผน** — ถ้าหาไม่เจอสักข้อ แปลว่าแผนไม่ครอบคลุม
      ลองใช้ `FR-011`, `FR-022`, `FR-029`, `FR-035`, `FR-037`
- [ ] **ช่อง N/A มีเหตุผลกำกับทุกช่อง** — "N/A" เปล่า ๆ คือการซ่อนงานที่ตกหล่น
- [ ] **ตัวเลขในหัวข้อสถานะปัจจุบันตรงกับของจริง** — รัน `dotnet test` เทียบดู
      (ถ้า AI เขียนว่า "~21" แต่รันจริงได้ 39 แปลว่ามันเดาจากเอกสารเก่า ให้สั่งแก้)
- [ ] **มีหัวข้อ "สิ่งที่ต้องตัดสินใจ"** — ถ้า AI ไม่ถามอะไรเลย แปลว่ามันเดาแทนคุณไปหมดแล้ว น่ากลัวกว่า
- [ ] **เลขบรรทัดที่อ้างถึงถูกต้องจริง** — สุ่มเปิด 2–3 จุด ถ้าผิด สั่งให้ `grep` ยืนยันแล้วแก้

## เมื่อแผนยังไม่ดีพอ — prompt สำหรับสั่งแก้

**ตกบางเรื่อง:**
```
ในแผนยังไม่เห็นเคสสำหรับ FR-035 (การปฏิเสธ pageSize นอกช่วง)
และ FR-037 (หน้าจอที่ต้องแสดงครบทุกรายการ)
เพิ่มเข้าไปในหัวข้อที่เหมาะสม พร้อมอ้าง FR ให้ครบ
```

**เคสตื้นเกินไป:**
```
เคสในหัวข้อ 6.4 (/stock) ตอนนี้ทดสอบแต่ทางที่สำเร็จ (happy path)
เพิ่มเคสทางที่ล้มเหลวให้ครบ: บาร์โค้ดซ้ำ ราคาไม่ถูกต้อง ลบสิ่งที่ไม่มีอยู่
และกรณีที่ Cashier พยายามเข้าถึง
```

**สงสัยว่ามันอ่าน spec จริงไหม:**
```
ยกมาให้ดูหน่อยว่า FR-022 เขียนว่าอะไรแบบคำต่อคำ
แล้วเคสไหนในแผนที่ทดสอบข้อนี้
```

## แบบฝึกหัด

**1.** รัน prompt แบบอ่อน (`เขียน unit test ให้โปรเจกต์นี้หน่อย`) ในโปรเจกต์นี้ แล้วเทียบกับ
`test-plan.md` ที่มีอยู่ — เขียนออกมาว่ามันตกเรื่องอะไรไปบ้าง อย่างน้อย 3 เรื่อง

**2.** เปิด `spec.md` หา FR ที่ยังไม่มีเคสในแผน (มีอยู่จริงหลายข้อ) แล้วเขียน prompt สั่งให้ AI เพิ่ม
โดยต้องระบุว่าให้ใส่ในหัวข้อไหนและใช้ ID รูปแบบใด

**3.** เลือกหน้าจอหนึ่งหน้าจาก `web/src/app/` ที่ยังไม่ได้อ่าน แล้วเขียน prompt ให้ AI ตรวจว่า
แถวของหน้าจอนั้นในเมทริกซ์ CRUD (§2) ถูกต้องหรือไม่ — ให้มันยืนยันด้วยโค้ดจริง ไม่ใช่แค่ตอบว่า "ถูกแล้ว"

**4.** (ยาก) สั่งให้ AI หาว่ามี FR ข้อใดบ้างที่ **ไม่มีเทสต์ในชั้นใดเลย** ทั้ง 265 เคส
คำใบ้: ต้องให้มันไล่ FR-001 ถึง FR-037 ทีละข้อ แล้วรายงานเป็นตาราง
