## 1. ความสัมพันธ์กับ `docs/qa/` ที่มีอยู่แล้ว

`docs/qa/01`–`06` คือ **เส้นทางทำมือ** — สอนนักเรียนว่าจะ prompt ยังไงให้ AI ทำงาน QA ได้ดี
คำสั่งทั้งสามคือ **เส้นทางอัตโนมัติ** ที่เดินบนกฎชุดเดียวกัน

| บทในคู่มือ | คำสั่งที่ทำงานแทน |
|---|---|
| `01-read-codebase.md` — สั่ง AI อ่าน codebase เพื่อวางแผนเทสต์ | `/qa-plan` |
| `02-write-tests.md` + `03-run-tests.md` — สั่งเขียนและรันเทสต์ | `/qa-implement` |
| `04-add-tests.md` — เพิ่มเคสเดียว / เพิ่มจากบั๊ก | `/qa-case` |
| `06-prompt-patterns.md` §6.1 (โครง prompt 5 ส่วน) | เป็นแม่แบบของเนื้อ `SKILL.md` ทั้งสามตัว |

**คู่มือไม่ถูกแทนที่** — ยังมีผู้อ่านที่คำสั่งไม่รองรับ (นักเรียนที่ต้องเข้าใจว่าทำไม ไม่ใช่แค่ได้ผลลัพธ์)
คำสั่งคือทางลัดสำหรับคนที่เข้าใจแล้ว

### กฎเหล็ก 3 ข้อที่ต้องฝังใน SKILL.md ทุกตัว

มาจาก `docs/qa/README.md` และ `.specify/memory/constitution.md` ข้อ III:

1. **เทสต์ต้องยืนยัน "สิ่งที่ spec บอกว่าควรเป็น" ไม่ใช่ "สิ่งที่โค้ดทำอยู่"**
   เมื่อโค้ดกับ spec ไม่ตรงกัน → **หยุดแล้วรายงาน ห้ามเลือกข้างเอง** (`04-add-tests.md` §4.1 ข้อ 1)
2. **ชั้น Domain และ Application ต้องรันได้โดยไม่มี PostgreSQL และไม่ต่อเน็ต** — ใช้ fake ที่ขอบ infrastructure
   (constitution ข้อ III ระบุว่า NON-NEGOTIABLE) ถ้าคำสั่งสร้างเทสต์ชั้น 1–2 ที่ต่อ DB จริง = ผลลัพธ์ผิด
3. **ห้ามลบหรือแก้เทสต์แดงเพื่อให้เขียว** — แดงเพราะโค้ดผิด → แก้โค้ด; แดงเพราะ spec ไม่ชัด → `Skip` พร้อมเหตุผล

## 3. `/qa-case` — รับเคสจากคน + triage

### หน้าที่

รับข้อความอิสระภาษาไทยจาก QA → ตรวจซ้ำ → จัดประเภท → เขียนลง inbox → **บอกคนแจ้งว่าเคสตกช่องไหน**

หัวใจของคำสั่งนี้คือ **triage** ไม่ใช่การรับเรื่อง ถ้าตัด triage ออก มันก็เป็นแค่สมุดจด

### อินพุต

| แหล่ง | ใช้ทำอะไร |
|---|---|
| `$ARGUMENTS` | ข้อความอิสระที่ QA พิมพ์ |
| `spec.md` | รายการ FR-001–FR-037 / SC-001–SC-010 ใช้ตัดสินว่าเคสมี FR รองรับไหม |
| `test-plan.md` | ตรวจว่าเคสนี้มีในแผนอยู่แล้วหรือยัง |
| `qa/case-inbox.md` | หาเลข `TC-M-NNN` ถัดไป + **ตรวจซ้ำกับ entry ที่ยัง `รอรับ`** (ถ้าไฟล์ไม่มี ให้สร้างจาก template) |
| `test-plan.md` §8 | ดู D-1…D-6 เพื่อตัดสินว่าเคส UI ถูกบล็อกอยู่ไหม |

### ขั้นตอน

1. **ตรวจซ้ำก่อน — ทั้งใน `test-plan.md` และใน inbox ที่ยัง `รอรับ`** ถ้าตรงกับของเดิม ให้ตอบว่าตรงกับ ID ไหน **แล้วจบ ไม่เพิ่ม entry**
   (เคสที่คนแจ้งเมื่อวานแต่ `/qa-plan` ยังไม่ได้รัน จะยังอยู่แค่ใน inbox เท่านั้น)
2. **triage เป็น 1 ใน 3 ช่อง** (ดูตารางข้างล่าง)
3. เฉพาะช่อง A เท่านั้นที่ได้ ID และถูกเขียนลง inbox
4. ถ้าเป็นเคสชั้น UI และ D-1/D-2/D-3 ยังไม่มีคำตอบ → รับเข้า inbox แต่ตั้งสถานะเป็น `บล็อก: D-1` และ**บอกคนแจ้งตั้งแต่ตอนนั้น** ไม่ปล่อยให้รอเก้อ
5. รายงานผล triage กลับให้คนแจ้งเป็นภาษาไทย

### ตาราง triage

| ช่อง | เงื่อนไข | ปลายทาง | ได้ ID ไหม |
|---|---|---|---|
| **A** | มี FR/SC รองรับอยู่แล้ว | เขียน entry ลง inbox รอ `/qa-plan` มาเก็บ | ✅ `TC-M-NNN` |
| **B** | **ขัดกับ FR** — คนแจ้งเข้าใจสเปกคนละแบบ | ไม่ใช่เทสต์ → แสดงข้อความ FR ที่ขัดกัน แล้วแนะนำ `/speckit-clarify` | ❌ |
| **C** | **ไม่มี FR ไหนครอบเลย** | นี่คือความต้องการที่หายไป → ต้องเข้า spec ไม่ใช่เข้าแผนเทสต์ | ❌ |

> ช่อง B และ C คือจุดที่คำสั่งนี้สร้างมูลค่าจริง — มันกันไม่ให้ "ความเข้าใจผิดของคนคนเดียว"
> กลายเป็นเทสต์ที่ทุกคนต้องมาแก้ทีหลัง

### กฎเหล็กเฉพาะคำสั่งนี้

- **ห้ามตั้ง FR ใหม่เอง** — ถ้าไม่มี FR ครอบ ต้องเข้าช่อง C เสมอ ห้ามเดาว่า "น่าจะอยู่ใต้ FR-0xx"
- **ห้ามเขียนลง `test-plan.md` โดยตรง** — inbox เท่านั้น
- **ห้ามใช้เลขใน namespace ของเคสที่ generate** (`TC-API-*`, `TC-UI-*` …) — ใช้ `TC-M-NNN` เท่านั้น

### รูปแบบ entry ใน `case-inbox.md`

```markdown
### TC-M-003 · กดปุ่มปิดบิลรัว ๆ 2 ครั้งแล้วได้บิลซ้ำ

- **สถานะ**: รอรับ
- **ชั้น**: UI
- **จุด**: `/sales`
- **ความสำคัญ**: P1
- **FR อ้างอิง**: FR-012
- **ที่มา**: bug
- **แจ้งเมื่อ**: 2026-09-11
- **รายละเอียด**: ในหน้าขาย ถ้ากดปุ่ม "ปิดบิล" ซ้ำเร็ว ๆ ก่อนที่ response แรกจะกลับมา จะได้บิล 2 ใบ
- **คาดหวัง**: ได้บิลเดียว ปุ่มต้องถูก disable ระหว่างรอ response
```

**ค่าที่เป็นไปได้ของ `สถานะ`**: `รอรับ` · `รับแล้ว → <TC-ID>` · `บล็อก: D-N` · `ปฏิเสธ: <เหตุผล>`
**ค่าที่เป็นไปได้ของ `ชั้น`**: `DOM` · `APP` · `API` · `UI` · `NFR` (ตรงกับ ID scheme เดิมใน test-plan.md)

เลข `NNN` เรียงต่อเนื่องกันทั้งไฟล์ **และห้ามถูกใช้ซ้ำแม้ entry นั้นจะถูกปฏิเสธไปแล้ว**

## 4. `/qa-plan` — รวมทุกแหล่งเข้า `test-plan.md`

### หน้าที่

อ่านเอกสาร speckit ทั้งหมด + inbox → **เติมแถวใหม่และติดธงแถวที่ล้าสมัย** ลงใน `test-plan.md`

### ⚠️ ต้องเป็น append ไม่ใช่ regenerate

นี่คือข้อแตกต่างสำคัญที่สุดจาก `/speckit-tasks` — พฤติกรรมต้องเลียน **`/speckit-converge`** แทน:

| ทำ | ไม่ทำ |
|---|---|
| เติมแถวใหม่ต่อท้ายหัวข้อที่เกี่ยวข้อง | เขียนทับทั้งไฟล์ |
| ติดธง `⚠️ ล้าสมัย` พร้อมเหตุผล บนแถวที่ FR อ้างอิงถูกลบ/แก้ | ลบแถวเดิมทิ้ง |
| อัปเดตยอดรวมใน §0 และ inventory ใน §1 | แตะ §8 (D-1…D-6) และ §9 |
| คงเลข ID เดิมทุกตัว | renumber ใหม่ |

ผลข้างเคียง: template `qa-test-plan-template.md` **ไม่ใช่แม่แบบไฟล์ทั้งไฟล์**
มันคือ **โครงหัวข้อ + schema ของแถว** ไว้บอกว่าแถวใหม่ต้องมีคอลัมน์อะไรและควรถูกวางใต้หัวข้อไหน

### อินพุต

รันครั้งเดียวที่ repo root:

```powershell
.specify/scripts/powershell/check-prerequisites.ps1 -Json -RequireSpec -RequireTasks -IncludeTasks -Template qa-test-plan-template
```

ได้ `FEATURE_DIR`, `AVAILABLE_DOCS`, `TEMPLATE_CONTENT`

> **`Resolve-TemplateContent` รับชื่อ template อะไรก็ได้ที่ตรง `^[a-z0-9-]+$`** (`common.ps1:521`)
> จึงไม่ต้องแก้ script เดิมเลย และได้ layering ของ `.specify/templates/overrides/` + `presets/` มาฟรี

**⚠️ `AVAILABLE_DOCS` ไม่ครบ** — จากโค้ดส่วน "Build list of available documents" มันคืนแค่
`research.md` · `data-model.md` · `contracts/` · `quickstart.md` · `tasks.md`

ดังนั้น SKILL.md **ต้องสั่งอ่านเพิ่มเองแบบระบุชัด**:

| ไฟล์ | ทำไมต้องระบุเอง |
|---|---|
| `$FEATURE_DIR/spec.md` | ถูกเช็คแค่ว่า "มีอยู่" ผ่าน `-RequireSpec` แต่ไม่อยู่ในลิสต์ |
| `$FEATURE_DIR/plan.md` | เช่นเดียวกัน (เช็คผ่าน `IMPL_PLAN`) |
| `$FEATURE_DIR/checklists/*.md` | ไม่อยู่ในลิสต์เลย ต้อง glob เอง |
| `$FEATURE_DIR/qa/case-inbox.md` | ไฟล์ของเราเอง speckit ไม่รู้จัก |
| `$FEATURE_DIR/test-plan.md` | ต้องอ่านของเดิมก่อน เพื่อ diff และไม่ใส่ซ้ำ |

### เอาต์พุต

1. `test-plan.md` ที่ถูกเติมแถว
2. `case-inbox.md` — แก้เฉพาะบรรทัด `สถานะ` ของ entry ที่เก็บแล้ว เป็น `รับแล้ว → TC-UI-SALES-042`
3. สรุปผลบนหน้าจอ: เพิ่มกี่แถว · ติดธงล้าสมัยกี่แถว · เก็บเคสจาก inbox กี่เคส · เคสไหนถูกบล็อก

### กฎการตั้ง ID

| ที่มา | รูปแบบ | วิธีให้เลข |
|---|---|---|
| generate จาก spec/contracts | `TC-<LAYER>-<AREA>-NNN` | นับต่อจากเลขสูงสุดของ area นั้น |
| คนแจ้งผ่าน `/qa-case` | `TC-M-NNN` | **คงเลขเดิมจาก inbox ห้ามเปลี่ยน** แค่ย้ายไปวางในหัวข้อที่ถูกต้อง |

### คอลัมน์ `ที่มา` (ของใหม่)

ตารางเคสเดิมมี `| ID | เคส | คาดหวัง | สถานะ | P |` → เพิ่มคอลัมน์ `ที่มา` ต่อท้าย

| ค่า | ความหมาย | ผลต่อ `/qa-implement` |
|---|---|---|
| `spec` | มาจาก FR/SC/contract โดยตรง | ปกติ |
| `manual` | คนแจ้งผ่าน `/qa-case` โดยไม่ได้เจอบั๊ก | ปกติ |
| `bug` | คนแจ้งเพราะ**เจอบั๊กจริง** | **ต้องแดงตั้งแต่รันครั้งแรก** (ดู §5) |
