# บทที่ 6 — สูตร prompt และกับดักที่พบบ่อย

## เป้าหมาย

สรุปสิ่งที่ได้เรียนมาทั้ง 5 บท เป็นสูตรที่หยิบไปใช้กับโปรเจกต์อื่นได้ และรู้ว่าอะไรคือ prompt ที่พังแน่นอน

---

## 6.1 โครงสร้าง prompt ที่ใช้ได้ผล — 5 ส่วน

prompt ที่ดีทุกอันในคู่มือนี้มีโครงเดียวกัน:

```
① บริบท     ให้อ่านอะไรก่อน (spec, contract, โค้ดตัวอย่าง)
② งาน       ทำอะไร ขอบเขตแค่ไหน
③ ข้อกำหนด   กติกาที่ห้ามฝ่าฝืน
④ ผลลัพธ์    อยากได้อะไรออกมา รูปแบบไหน
⑤ จุดหยุด   ทำถึงไหนแล้วหยุดรอ
```

ตัวอย่างที่ครบทั้ง 5 ส่วน:

```
① อ่าน spec.md ข้อ FR-029 และ contracts/products.md

② เขียนเทสต์ตาม test-plan.md เคส TC-API-PROD-012 ถึง 016 เท่านั้น

③ ข้อกำหนด:
   - สืบทอดจาก ApiTestBase ห้ามสร้าง WebApplicationFactory ใหม่
   - ค่าที่ assert ต้องมาจาก contract ไม่ใช่จากโค้ดปัจจุบัน
   - ถ้าเทสต์แดงเพราะโค้ดไม่ตรงสเปก ให้รายงาน ห้ามแก้เทสต์ให้ผ่าน

④ ผลลัพธ์: ไฟล์เทสต์ + ผลรัน dotnet test + อัปเดตสถานะใน test-plan.md

⑤ เสร็จแล้วหยุด รอฉันตรวจก่อนทำหัวข้อถัดไป
```

**ส่วนที่คนลืมบ่อยที่สุดคือ ⑤** ถ้าไม่ใส่ AI จะทำต่อยาว ๆ เป็นชั่วโมง แล้วถ้าผิดตั้งแต่ต้น
คุณต้องทิ้งงานทั้งหมด

---

## 6.2 ประโยคติดอาวุธ — copy ไปใช้ได้เลย

ประโยคเหล่านี้แต่ละอันปิดช่องโหว่ที่เกิดขึ้นจริง เอาไปวางท้าย prompt ได้ทันที

### กันไม่ให้เทสต์แค่ถ่ายรูปโค้ด

```
ค่าที่ assert ต้องมาจาก spec.md หรือ contracts/*.md ไม่ใช่จากพฤติกรรมของโค้ดปัจจุบัน
ถ้าสองอย่างไม่ตรงกัน ให้รายงาน อย่าเลือกข้างเอง
```

### กันไม่ให้แก้เทสต์ให้เขียว

```
ถ้าเทสต์แดง ห้ามแก้ไฟล์เทสต์เพื่อให้ผ่าน
ให้วิเคราะห์ว่าโค้ดผิดหรือสเปกกำกวม แล้วรายงานกลับมา
```

### กันไม่ให้ทำเกินขอบเขต

```
ทำเฉพาะที่สั่ง ถ้าเห็นอย่างอื่นที่ควรแก้ ให้บอกมา อย่าลงมือแก้เอง
```

### กันไม่ให้เดาเมื่อข้อมูลไม่พอ

```
ถ้ามีจุดไหนที่สเปกไม่ได้ระบุชัด ให้หยุดแล้วถาม อย่าเลือกทางที่ดูสมเหตุสมผลที่สุดเอง
```

### บังคับให้พิสูจน์ผลงาน

```
รันเทสต์แล้วยกผลจริงมาให้ดู อย่าสรุปว่า "น่าจะผ่าน"
```

### บังคับให้วินิจฉัยก่อนรักษา

```
ตอบก่อนว่าปัญหาคืออะไร มาจากไหน มีทางแก้กี่ทาง แต่ละทางแลกอะไร
แล้วหยุด รอให้ฉันเลือกก่อน
```

### กันเทสต์แดงสลับเขียว

```
ห้ามใช้ waitForTimeout หรือ sleep รอเวลาแบบตายตัว ให้รอเงื่อนไขแทน
ห้ามแก้ปัญหา flaky ด้วยการเพิ่ม retry หรือยืด timeout
```

### รักษาให้แผนกับโค้ดตรงกัน

```
อัปเดต test-plan.md ทุกครั้งที่เพิ่มหรือแก้เทสต์ ทั้ง ID ใหม่และการเปลี่ยนสถานะ
```

## 6.3 กับดัก 8 ข้อที่พบบ่อยที่สุด

| # | กับดัก | อาการ | ทางแก้ |
|---|---|---|---|
| 1 | **สั่งจากโค้ด ไม่ใช่จากสเปก** | เทสต์เขียวหมดตั้งแต่วันแรกและตลอดไป | ชี้ FR ที่ต้องอ่านทุกครั้ง |
| 2 | **สั่งทีเดียวทั้งชุด** | ได้ไฟล์ 20 ไฟล์ที่ตรวจไม่ไหว ผิดเหมือนกันหมด | สั่งทีละหัวข้อ 10–25 เคส |
| 3 | **ไม่บอกให้หยุด** | AI ทำยาว 2 ชั่วโมง ผิดตั้งแต่ 10 นาทีแรก | ใส่จุดหยุดทุก prompt |
| 4 | **ปล่อยให้แก้เทสต์เอง** | "ผ่านหมดแล้ว" ทั้งที่บั๊กยังอยู่ครบ | ห้ามแก้ไฟล์เทสต์ เขียนไว้ชัด ๆ |
| 5 | **ไม่บอกชั้นของเทสต์** | unit test ต่อ database ผิด constitution ข้อ III | ระบุชั้นและข้อจำกัดทุกครั้ง |
| 6 | **ไม่บอกให้ใช้ของเดิม** | สร้าง `WebApplicationFactory` ซ้อนอันที่มีอยู่ | ชี้ไฟล์ตัวอย่างให้ดู |
| 7 | **ลืมอัปเดตแผน** | 3 เดือนผ่านไป แผนกลายเป็นเอกสารที่โกหก | ใส่ข้อกำหนดอัปเดตแผนใน prompt |
| 8 | **เชื่อคำสรุปของ AI** | "เสร็จแล้ว ครอบคลุมทุกกรณี" ทั้งที่ตก FR ไป 12 ข้อ | ใช้ checklist หัวข้อ 6.4 ทุกครั้ง |

## 6.4 Checklist ตรวจงาน AI — ใช้ได้โดยไม่ต้องอ่านโค้ดเทสต์เป็น

นักเรียนส่วนใหญ่ยังอ่านโค้ดเทสต์แล้วตัดสินคุณภาพไม่ได้ checklist นี้จึงออกแบบให้ตรวจแบบ **กลไก**
ทุกข้อตอบได้ด้วยการนับหรือค้นหา ไม่ต้องใช้วิจารณญาณ

### ตรวจแผน

- [ ] ทุกแถวมี FR หรือ SC อ้างอิง — ค้นหาแถวที่ช่อง FR ว่าง ต้องได้ศูนย์
- [ ] ช่อง N/A มีเหตุผลกำกับทุกช่อง — ค้นคำว่า `N/A` แล้วดูว่ามีคำอธิบายต่อท้ายไหม
- [ ] สุ่ม FR มา 5 ข้อ หาเจอในแผนครบ
- [ ] มีหัวข้อ "สิ่งที่ต้องตัดสินใจ" — ถ้าไม่มีเลย แปลว่า AI เดาแทนคุณหมดแล้ว

### ตรวจโค้ดเทสต์

- [ ] จำนวนเทสต์ที่รันได้ = จำนวนเคสที่สั่ง (สั่ง 5 ต้องได้ 5)
- [ ] ทุกเทสต์มีรหัส TC ในชื่อหรือใน comment
- [ ] ค้นคำว่า `DbContext` / `Npgsql` / `ConnectionString` ในชั้น Domain กับ Application → ต้องไม่เจอ
- [ ] ไม่มีเทสต์ที่ assert แค่ `NotBeNull()` แล้วจบ
- [ ] ค้นคำว่า `waitForTimeout` / `Thread.Sleep` → ต้องไม่เจอ
- [ ] `git diff` แล้วไม่มีเทสต์เดิมถูกลบหรือถูก skip เพิ่ม

### ตรวจการรัน

- [ ] รันสองรอบติดกันได้ผลเหมือนกัน
- [ ] `Skipped` ทุกตัวมีเหตุผลกำกับ
- [ ] ปิด PostgreSQL แล้วชั้น 1–2 ยังเขียว

### ตรวจว่าเทสต์ตรวจอะไรจริง — ข้อที่สำคัญที่สุด

- [ ] **แก้โค้ดให้พังโดยตั้งใจ 1 จุด แล้วเทสต์ต้องแดง**

ถ้าข้อสุดท้ายไม่ผ่าน ข้ออื่นผ่านหมดก็ไม่มีความหมาย เพราะคุณมีชุดเทสต์ที่ไม่ตรวจอะไรเลย

## 6.5 กรณีศึกษาจากโปรเจกต์นี้

ตัวอย่างจริงที่เกิดขึ้นระหว่างสร้าง `test-plan.md` ของ TaladPOS

### กรณีที่ 1 — prompt ที่ต่างกันนิดเดียว ให้ผลต่างกันคนละเรื่อง

| prompt | สิ่งที่ AI เห็น | เทสต์ที่ได้ | มีค่าไหม |
|---|---|---|---|
| `เขียนเทสต์ให้ Cart.tsx` | โค้ดแสดง subtotal | assert ว่าแสดง subtotal → **เขียว** | ❌ ล็อกช่องว่างไว้ |
| `เขียนเทสต์ตาม FR-006` | สเปกบอกต้องมี 3 ค่า | assert ว่าต้องมี 3 ค่า → **แดง** | ✅ เปิดโปงช่องว่าง |

ความจริงคือ `Cart.tsx:222` แสดงแค่ยอดรวมย่อย ขณะที่ FR-006 กำหนดว่าต้องแสดงยอดรวมย่อย
ส่วนลด และยอดสุทธิ ครบสามค่า — **เทสต์แดงตัวนั้นมีค่ามากกว่าเทสต์เขียวสิบตัว**

---

### กรณีที่ 2 — เมื่อเอกสารกับโค้ดไม่ตรงกัน AI ต้องรายงาน ไม่ใช่เลือกข้าง

พบระหว่างวางแผนว่า:

- `contracts/sales.md` เขียนว่า 409 คืน `{"error":"insufficient_stock","productId":…}` แบน
- `ErrorHandlingMiddleware.cs:31` ส่ง `{"error":"insufficient_stock","details":{"productId":…}}` ซ้อน

ถ้า AI เขียนเทสต์ตามโค้ด → เทสต์เขียว แต่ล็อกรูปแบบที่ contract ไม่รับรอง
ถ้าเขียนตาม contract → เทสต์แดง แต่ไม่มีใครรู้ว่าฝั่งไหนถูก

**ทางที่ถูกคือทางที่สาม**: บันทึกเป็น `R-08` ในแผน แล้วรอการตัดสินใจของคน
พร้อม mark เทสต์ที่เกี่ยวข้องเป็น `Skip` โดยอ้าง `R-08` ไว้

> **บทเรียน**: "หยุดแล้วถาม" คือคำตอบที่ถูกต้องเสมอเมื่อสเปกกำกวม
> prompt ต้องเปิดทางให้ AI ตอบแบบนี้ได้ ไม่ใช่บีบให้มันต้องเลือกข้าง

---

### กรณีที่ 3 — ตัวเลขที่ AI เดาจากเอกสารเก่า

ครั้งแรกที่ AI สรุปสถานะเทสต์ปัจจุบัน มันเขียนว่า:

```
Application: ~21 เทสต์      ← เดาจาก tasks.md ที่บันทึกไว้ตอนทำฟีเจอร์
Integration: ~8 เทสต์
```

พอรันจริงด้วย `dotnet test`:

```
Application: 39 เทสต์       ← ของจริง
Integration:  9 เทสต์
```

ต่างกันเกือบเท่าตัว เพราะมีเทสต์ที่เพิ่มระหว่างทางโดยไม่ได้อัปเดต `tasks.md`

> **บทเรียน**: ตัวเลขที่ AI ให้มาโดยไม่ได้รันคำสั่งจริง คือการเดาที่ดูน่าเชื่อถือ
> เมื่อไรที่ตัวเลขสำคัญ ให้สั่งว่า **"รันคำสั่งจริงแล้วยกผลมา"** ทุกครั้ง

## 6.6 Template เปล่า

เอาไปเติมใช้กับโปรเจกต์อื่นได้เลย

```
① อ่าน [ไฟล์สเปก] และ [ไฟล์ contract] ก่อน

② [งานที่ต้องทำ] เฉพาะ [ขอบเขตที่ชัดเจน] เท่านั้น

③ ข้อกำหนด:
   - ค่าที่ assert ต้องมาจากสเปก ไม่ใช่จากโค้ดปัจจุบัน
   - ทำตามสไตล์ของ [ไฟล์ตัวอย่างที่มีอยู่]
   - [ข้อจำกัดเฉพาะของชั้นนี้ เช่น ห้ามต่อ database]
   - ถ้าเทสต์แดงเพราะโค้ดไม่ตรงสเปก ให้รายงาน ห้ามแก้เทสต์
   - ถ้าสเปกกำกวม ให้หยุดถาม อย่าเดา

④ ผลลัพธ์ที่ต้องการ:
   - โค้ดเทสต์ + ผลรันจริง
   - อัปเดต [ไฟล์แผน]

⑤ เสร็จแล้วหยุด รอตรวจก่อนทำส่วนถัดไป
```

---

## แบบฝึกหัด

**1.** เอา prompt ที่คุณเคยเขียนเองมาปรับให้ครบทั้ง 5 ส่วน แล้วรันเทียบกับของเดิม บันทึกว่าผลต่างกันอย่างไร

**2.** ใช้ checklist หัวข้อ 6.4 ตรวจงานที่ทำไว้ในบทที่ 2 — ผ่านกี่ข้อจากทั้งหมด

**3.** จำลองกับดักข้อ 4 (ปล่อยให้ AI แก้เทสต์เอง): แก้โค้ด production ให้ผิด แล้วสั่งว่า
`เทสต์แดง แก้ให้หน่อย` เฉย ๆ — บันทึกว่ามันแก้ฝั่งไหน

**4.** เขียนประโยคติดอาวุธเพิ่มอีก 3 ประโยคจากปัญหาที่คุณเจอเอง พร้อมอธิบายว่าปิดช่องโหว่อะไร

**5.** (ยาก) เอาคู่มือชุดนี้ไปใช้กับโปรเจกต์อื่นที่ไม่มี spec เขียนไว้เลย — เขียนสรุปว่า
ต้องปรับอะไรบ้าง และ **ขั้นตอนไหนทำไม่ได้เลยถ้าไม่มีสเปก** (คำใบ้: อ่านบทเรียนหลักในหน้าสารบัญอีกครั้ง)
