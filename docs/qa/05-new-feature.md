# บทที่ 5 — เมื่อมีฟีเจอร์ใหม่

## เป้าหมาย

รู้ว่าฟีเจอร์ใหม่ต้องผ่านขั้นตอนอะไรบ้าง และ **เทสต์เข้ามาตรงจุดไหนของวงจร**

---

## วงจรที่โปรเจกต์นี้ใช้จริง

TaladPOS ใช้ **Spec-Driven Development (speckit)** ซึ่งเห็นได้จากประวัติ commit
(`chore: auto-commit after /speckit-implement run`) อย่าสร้างวงจรใหม่ขึ้นมาเอง ให้เสียบเข้ากับของเดิม

```
  ①  /speckit-specify      เขียนข้อกำหนด → เกิด FR-0xx ใหม่
             ↓
  ②  /speckit-clarify      ถามจุดที่กำกวมจนชัด
             ↓
  ③  /speckit-plan         ออกแบบ → เกิด contracts/*.md
             ↓
  ④  เพิ่มเคสใน test-plan.md          ← 🎯 เทสต์เข้าตรงนี้ ไม่ใช่ตอนท้าย
             ↓
  ⑤  /speckit-tasks        แตกงาน (task เขียนเทสต์มาก่อน task เขียนโค้ด)
             ↓
  ⑥  เขียนเทสต์ให้แดงก่อน               ← 🎯 แดงคือสิ่งที่ถูกต้องในขั้นนี้
             ↓
  ⑦  /speckit-implement    เขียนโค้ดจนเทสต์เขียว
             ↓
  ⑧  /speckit-analyze      ตรวจว่า spec/plan/tasks ยังตรงกัน
             ↓
  ⑨  รันชุดเต็มก่อน deploy
```

**ทำไมเทสต์ต้องอยู่ขั้น ④ และ ⑥ ไม่ใช่ขั้น ⑧**

`.specify/memory/constitution.md` ข้อ III ระบุว่า:

> All business logic MUST have unit test coverage. A change to business logic
> **MUST NOT be merged without accompanying unit tests** — NON-NEGOTIABLE

และ `tasks.md` ของฟีเจอร์แรกก็จัดลำดับแบบนี้จริง — หัวข้อ "Tests for User Story N" มาก่อน
หัวข้อ implementation เสมอ

**เหตุผลเชิงปฏิบัติ**: เทสต์ที่เขียน *ก่อน* โค้ด บังคับให้คุณตอบว่า "ถูกต้องแปลว่าอะไร" ตั้งแต่แรก
เทสต์ที่เขียน *หลัง* โค้ด แค่ยืนยันว่า "โค้ดทำสิ่งที่มันทำ" ซึ่งเป็นประโยคที่จริงเสมอและไม่มีค่า

---

## ตัวอย่างครบวงจร: เพิ่มฟีเจอร์ "ยกเลิกบิล"

สมมติร้านขอฟีเจอร์ยกเลิกบิล ซึ่งเวอร์ชันนี้ตัดสินใจไว้ว่า *ไม่รองรับ* (clarify #2) จึงเป็นตัวอย่างที่ดี
เพราะต้องแก้ทั้งสเปกและระบบ

---

### ขั้น ①–② เขียนข้อกำหนด

```
/speckit-specify เพิ่มฟีเจอร์ยกเลิกบิลขาย: ผู้จัดการยกเลิกบิลที่ชำระเงินแล้วได้
ภายใน 24 ชั่วโมง เมื่อยกเลิกต้องคืนสต็อกสินค้าทุกรายการในบิล
และหักยอดสะสมของสมาชิกออกตามยอดบิลนั้น
```

⚠️ **จุดที่ต้องระวัง**: `spec.md` ปัจจุบันเขียนไว้ชัดว่า *"บิลที่ชำระเงินสำเร็จถือเป็นที่สิ้นสุด
แก้ไข/ยกเลิกไม่ได้"* ต้องแก้ข้อความเดิมนั้นด้วย ไม่ใช่เพิ่ม FR ใหม่ทับไว้เฉย ๆ ไม่งั้นสเปกจะขัดกันเอง
ให้บอก AI ตรง ๆ:

```
ก่อนเพิ่ม FR ใหม่ ให้หาก่อนว่า spec.md มีข้อความไหนที่ขัดกับฟีเจอร์นี้บ้าง
แล้วเสนอมาว่าจะแก้ข้อความเดิมอย่างไร ยังไม่ต้องแก้จริง
```

---

### ขั้น ③ ออกแบบ

```
/speckit-plan
```

ได้ `contracts/sales.md` ที่เพิ่ม `POST /api/v1/sales/{id}/cancel` พร้อม status code ครบ

---

### ขั้น ④ เพิ่มเคสในแผน — **ก่อนเขียนโค้ดใด ๆ**

```
อ่าน FR ใหม่ที่เพิ่งเพิ่มใน spec.md และ contracts/sales.md ส่วน cancel
แล้วเพิ่มเคสลง test-plan.md ให้ครบทั้ง 4 ชั้น

ต้องครอบคลุมอย่างน้อย:
- Domain: กติกาการยกเลิก (เกิน 24 ชม.ไม่ได้, ยกเลิกซ้ำไม่ได้)
- Application: use case คืนสต็อกและหักยอดสะสมครบใน transaction เดียว
- API: 200/400/403/404 + Cashier ต้องได้ 403 ตาม FR-029
- UI: ปุ่มยกเลิกในหน้าประวัติการขาย + กล่องยืนยัน + ผลลัพธ์หลังยกเลิก

และอัปเดตเมทริกซ์ CRUD หัวข้อ 2 ด้วย
เพราะแถว /sales/history เดิมเขียนว่า Delete เป็น N/A ตอนนี้ไม่ใช่แล้ว

ใช้ ID ที่ยังไม่ถูกใช้ และอ้าง FR ให้ครบทุกแถว
```

**บรรทัดเรื่องเมทริกซ์ CRUD คือสิ่งที่คนลืมบ่อยที่สุด** — เอกสารเก่าที่ไม่ได้อัปเดต
อันตรายกว่าไม่มีเอกสารเลย เพราะคนเชื่อมัน

---

### 🔮 ผลที่คาด

```
test-plan.md แก้ไข:
  §2  แถว /sales/history: Delete จาก "N/A — บิล append-only"
      → "ยกเลิกบิลภายใน 24 ชม. (Manager เท่านั้น)"
  §3  + TC-DOM-SALE-007 ถึง 009    (3 เคส)
  §4  + TC-APP-SALE-009 ถึง 012    (4 เคส)
  §5  + TC-API-SALE-023 ถึง 029    (7 เคส)
  §6  + TC-UI-HIST-012 ถึง 016     (5 เคส)

รวม 19 เคสใหม่ · แผนจาก 265 → 284 เคส
```

---

### ขั้น ⑤–⑥ เขียนเทสต์ให้แดงก่อน

```
เขียนเทสต์ตามเคสใหม่ที่เพิ่งเพิ่ม เริ่มจากชั้น Domain ก่อน

ตอนนี้ยังไม่มีโค้ด Sale.Cancel() ดังนั้นเทสต์ต้องคอมไพล์ไม่ผ่านหรือแดง
ซึ่งถูกต้องแล้วสำหรับขั้นนี้ ห้ามเขียนโค้ด production เพื่อให้มันเขียว

ให้สร้างแค่ signature ว่างที่ throw NotImplementedException พอ
เพื่อให้คอมไพล์ผ่านและเห็นว่าเทสต์แดงเพราะยังไม่ได้ทำ ไม่ใช่แดงเพราะเขียนผิด
```

🔮 **ผลที่คาด** — และนี่คือผลลัพธ์ที่ *ถูกต้อง* ในขั้นนี้:

```
Failed!  - Failed: 3, Passed: 45, Skipped: 0, Total: 48

  ✗ TC-DOM-SALE-007 ยกเลิกบิลภายใน 24 ชม. สำเร็จ
      System.NotImplementedException
  ✗ TC-DOM-SALE-008 ยกเลิกบิลเกิน 24 ชม. ถูกปฏิเสธ
      System.NotImplementedException
  ✗ TC-DOM-SALE-009 ยกเลิกบิลที่ยกเลิกไปแล้ว ถูกปฏิเสธ
      System.NotImplementedException
```

**สอนนักเรียนให้เห็นว่าหน้าจอสีแดงนี้คือความคืบหน้า ไม่ใช่ความล้มเหลว**
มันคือรายการงานที่ชัดเจนว่าต้องทำอะไรบ้าง และเป็นเกณฑ์ที่บอกได้ว่าเมื่อไรถึงเรียกว่าเสร็จ

---

### ขั้น ⑦ เขียนโค้ดจนเขียว

```
/speckit-implement
```

หรือถ้าอยากคุมทีละขั้น:

```
ทำให้ TC-DOM-SALE-007 ถึง 009 เขียว โดยแก้เฉพาะ Sale.cs

เงื่อนไข:
- ห้ามแก้ไฟล์เทสต์
- ห้ามแตะเทสต์ 45 ตัวเดิม ต้องยังเขียวครบ
- รันแล้วรายงานผลก่อนไปชั้นถัดไป
```

**"ห้ามแก้ไฟล์เทสต์"** คือบรรทัดที่ป้องกันปัญหาใหญ่ที่สุดของการใช้ AI เขียนโค้ด —
เมื่อเจอทางตัน มันจะแก้เทสต์ให้เข้ากับโค้ดแทนที่จะแก้โค้ดให้เข้ากับเทสต์

---

### ขั้น ⑧ ตรวจความสอดคล้อง

```
/speckit-analyze
```

แล้วตามด้วย:

```
ตรวจเพิ่มอีก 3 อย่างที่ speckit-analyze ไม่ได้ดู:
1. FR ใหม่ทุกข้อมีเทสต์ครอบคลุมจริงไหม ยืนยันด้วยรหัส TC
2. test-plan.md มีเคสไหนที่สถานะยังเป็น "ใหม่" ทั้งที่เขียนโค้ดไปแล้ว
3. เมทริกซ์ CRUD (§2) ยังตรงกับความจริงหลังเพิ่มฟีเจอร์นี้ไหม
```

---

```bash

```

## เมื่อฟีเจอร์ใหม่ทำให้เทสต์เดิมแดง

เกิดขึ้นได้ และไม่ได้แปลว่าผิดเสมอไป

```
หลังเพิ่มฟีเจอร์ยกเลิกบิล เทสต์เดิม TC-API-SALE-022 แดง
(เทสต์ที่ยืนยันว่า "ไม่มี endpoint ยกเลิกบิล")

วิเคราะห์ว่าเป็นกรณีไหนใน 3 กรณีนี้:
ก) เทสต์เดิมล้าสมัยแล้ว เพราะพฤติกรรมที่ถูกต้องเปลี่ยนไปจริงตามสเปกใหม่
ข) ฟีเจอร์ใหม่ทำของเดิมพัง เป็นบั๊กที่ต้องแก้
ค) เทสต์เดิมผูกกับรายละเอียดภายในมากเกินไป ควรเขียนใหม่

อ้าง spec.md ประกอบด้วยว่าตัดสินจากข้อความไหน
แล้วเสนอทางแก้ ยังไม่ต้องลงมือ
```

🔮 คำตอบที่ควรได้สำหรับกรณีนี้: **(ก)** — `TC-API-SALE-022` เขียนขึ้นตอนที่สเปกบอกว่าบิลเป็น
append-only เมื่อสเปกเปลี่ยน เทสต์ต้องเปลี่ยนตาม แต่ต้อง **แก้ให้ตรงกับสเปกใหม่**
ไม่ใช่ลบทิ้ง — เปลี่ยนจาก "ต้องไม่มี endpoint นี้" เป็น "ต้องมี และต้องจำกัดสิทธิ์เฉพาะ Manager"

## วิธีตรวจว่าฟีเจอร์ใหม่พร้อม deploy

- [ ] FR ใหม่ทุกข้อมีเทสต์อย่างน้อย 1 เคส และมีทั้งทางสำเร็จและทางล้มเหลว
- [ ] `test-plan.md` อัปเดตครบ — เคสใหม่ สถานะ และเมทริกซ์ CRUD
- [ ] เทสต์เดิมเขียวครบ หรือถ้าแดง มีคำอธิบายที่อ้างสเปกได้
- [ ] ชั้น Domain/Application ยังรันได้โดยไม่มี PostgreSQL
- [ ] endpoint ใหม่มีเทสต์สิทธิ์ครบ — ไม่ล็อกอิน = 401, ผิดบทบาท = 403
- [ ] `/speckit-analyze` ผ่าน
- [ ] รันชุดเต็มสองรอบติดกันได้ผลเหมือนกัน

## แบบฝึกหัด

**1.** เลือกฟีเจอร์เล็ก ๆ ขึ้นมาเอง (เช่น "ค้นหาสมาชิกจากยอดสะสมขั้นต่ำ") แล้วเดินครบทั้ง 9 ขั้น
โดยหยุดที่ขั้น ⑥ — ส่งงานเป็นหน้าจอที่แสดงเทสต์แดงพร้อมคำอธิบายว่าทำไมแดงถึงถูกต้อง

**2.** ทำแบบฝึกหัด 1 ต่อจนถึงขั้น ⑦ — ทำให้เขียวโดยห้ามแก้ไฟล์เทสต์แม้แต่บรรทัดเดียว

**3.** จงใจเพิ่มฟีเจอร์ที่ขัดกับสเปกเดิม แล้วดูว่า AI ทักท้วงเองไหม หรือทำตามเงียบ ๆ
บันทึกผล — นี่คือเหตุผลที่ขั้น ① ต้องสั่งให้มันหาข้อความที่ขัดกันก่อน

**4.** (ยาก) เขียน prompt สำหรับตรวจว่า **มี endpoint ไหนในระบบที่ไม่มีเทสต์สิทธิ์เลย**
คำใบ้: ให้ AI ไล่จาก `[Authorize]` attribute ในทุก controller เทียบกับเทสต์ที่มีอยู่
