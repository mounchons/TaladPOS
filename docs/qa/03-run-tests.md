# บทที่ 3 — สั่งรัน อ่านผล และแก้เมื่อแดง

## เป้าหมาย

รันชุดเทสต์ได้ทั้งชุดก่อน build/deploy อ่านผลออกว่าอะไรพัง และสั่ง AI แก้ได้อย่างปลอดภัย

---

## 3.1 คำสั่งรัน

### รันชุดฝั่ง API ทั้งหมด (ใช้ได้จริงวันนี้)

```bash
docker compose up -d postgres      # ต้องรันก่อน ไม่งั้นชั้น Integration จะแดง
cd api && dotnet test TaladPOS.sln
```

✅ **ผลจริง** จากการรันเมื่อ 2026-09-10:

```
Passed!  - Failed: 0, Passed: 45, Skipped: 0, Total: 45, Duration: 305 ms - TaladPOS.Domain.Tests.dll
Passed!  - Failed: 0, Passed: 39, Skipped: 0, Total: 39, Duration:  25 ms - TaladPOS.Application.Tests.dll
Passed!  - Failed: 0, Passed:  9, Skipped: 0, Total:  9, Duration:   3 s  - TaladPOS.Api.IntegrationTests.dll
```

**อ่านผลนี้อย่างไร** — ตัวเลข Duration บอกอะไรเยอะกว่าที่คิด:

| ชั้น | เวลา | ทำไม |
|---|---|---|
| Domain 45 เทสต์ | 305 ms | ไม่แตะ I/O เลย เป็นการคำนวณล้วน |
| Application 39 เทสต์ | 25 ms | ใช้ fake ทั้งหมด **เร็วกว่า Domain เพราะไม่ต้องโหลด assembly เพิ่ม** |
| Integration 9 เทสต์ | 3 วินาที | ต่อ PostgreSQL จริง รัน migration จริง |

> 🚩 **สัญญาณอันตราย**: ถ้าวันหนึ่ง Application ใช้เวลาเป็นวินาที แปลว่ามีเทสต์แอบต่อ database
> ซึ่งผิด constitution ข้อ III ให้สั่ง AI หาว่าตัวไหนแล้วเปลี่ยนไปใช้ fake

### รันเฉพาะชั้น

```bash
cd api
dotnet test tests/TaladPOS.Domain.Tests
dotnet test tests/TaladPOS.Application.Tests
dotnet test tests/TaladPOS.Api.IntegrationTests
```

### รันเฉพาะเทสต์ที่สนใจ

```bash
cd api
dotnet test tests/TaladPOS.Domain.Tests --filter "FullyQualifiedName~Promotion"
dotnet test tests/TaladPOS.Domain.Tests --filter "FullyQualifiedName~DiscountResolver"
```

✅ **ผลจริง**: คำสั่งแรกได้ 24 เทสต์ · คำสั่งที่สองได้ 9 เทสต์

> 🚩 ถ้า filter ไม่ตรงกับเทสต์ตัวใดเลย `dotnet test` จะขึ้น `No test matches the given testcase filter`
> **แล้ว exit code เป็น 0 เหมือนผ่าน** — ระวังอย่าเข้าใจผิดว่า "รันแล้วผ่านหมด"
> ทั้งที่จริงคือ "ไม่ได้รันอะไรเลย" ให้ดูตัวเลข Total ทุกครั้ง

### รันฝั่ง web

🔮 **ยังใช้ไม่ได้** — ต้องตั้งค่าตามบทที่ 2 หัวข้อ 2.3 ก่อน หลังตั้งค่าแล้วจะเป็น:

```bash
cd web
npm run test           # Vitest — unit ของ lib/components
npm run test:e2e       # Playwright — ทั้งชุด
npm run test:e2e -- --grep @smoke     # เฉพาะ smoke
npx playwright show-report            # เปิดรายงานพร้อมภาพหน้าจอตอนพัง
```

## 3.2 รันทั้งหมดก่อน deploy

เป้าหมายคือคำสั่งเดียวจบ ให้สั่ง AI สร้างให้:

```
สร้าง script สำหรับรันเทสต์ทั้งหมดก่อน deploy ชื่อ scripts/test-all.sh

ต้องทำตามลำดับนี้ และหยุดทันทีถ้าขั้นไหนล้ม:
1. docker compose up -d postgres แล้วรอจน healthy จริง (อย่าใช้ sleep ตายตัว)
2. cd api && dotnet test TaladPOS.sln
3. cd web && npx tsc --noEmit
4. cd web && npm run build
5. cd web && npx eslint src --max-warnings=0
6. cd web && npm run test:e2e

ท้าย script สรุปเป็นตารางว่าแต่ละขั้นผ่านหรือไม่ และใช้เวลาเท่าไร
exit code ต้องไม่เป็น 0 ถ้ามีขั้นใดล้ม เพื่อให้ CI จับได้
```

**"หยุดทันทีถ้าขั้นไหนล้ม" สำคัญ** — ถ้าไม่ใส่ script จะรันจนจบแล้วบอกว่าผ่าน
ทั้งที่ขั้นที่ 2 แดงไปแล้ว

**"อย่าใช้ sleep ตายตัว" ก็สำคัญ** — `sleep 5` จะพอบนเครื่องคุณ แต่ไม่พอบน CI ที่ช้ากว่า
กลายเป็น script ที่ล้มแบบสุ่ม

---

## 3.3 แบ่งเป็น smoke กับ full

รันครบ 265 เคสน่าจะใช้เวลา 15–25 นาที ซึ่งนานเกินกว่าจะรันทุกครั้งที่แก้โค้ด แบ่งสองระดับ:

| ระดับ | จำนวน | เวลา | รันเมื่อไหร่ |
|---|---|---|---|
| **smoke** | ~20 เคส | 2–3 นาที | ทุกครั้งที่ commit |
| **full** | 265 เคส | 15–25 นาที | ก่อน build/deploy · ทุกคืน |

```
เพิ่ม tag @smoke ให้เทสต์ E2E ที่เป็นเส้นทางสำคัญที่สุด เลือกประมาณ 20 เคส

เกณฑ์การเลือก: ถ้าเคสนี้พัง แปลว่าระบบใช้งานไม่ได้เลย
ตัวอย่างที่ควรอยู่ในนี้ — ล็อกอินทั้งสองบทบาท, ขายครบวงจร 1 บิล,
CRUD สินค้าครบ 1 รอบ, Cashier ถูกปฏิเสธจาก 3 หน้าจอของ manager

เพิ่ม npm script "test:smoke" ที่รันเฉพาะ tag นี้
แล้วบอกด้วยว่าเลือกเคสไหนบ้าง เพราะอะไร
```

## 3.4 เมื่อเทสต์แดง — prompt ที่ปลอดภัย

นี่คือจุดที่นักเรียนพลาดบ่อยที่สุด

### ❌ Prompt อันตราย

```
เทสต์แดง แก้ให้หน่อย
```

**จะเกิดอะไร**: AI มีสองทางให้เลือก — แก้โค้ดให้ถูก หรือแก้เทสต์ให้ผ่าน
ทางที่สองง่ายกว่ามาก และมันมักเลือกทางนั้น คุณจะได้ "เขียวทั้งหมด" พร้อมบั๊กที่ยังอยู่ครบ

---

### ✅ Prompt ที่ปลอดภัย

```
เทสต์ TC-API-PROD-015 แดง

ก่อนแก้อะไรทั้งสิ้น ให้ตอบ 3 ข้อนี้ก่อน:
1. เทสต์คาดหวังอะไร และได้อะไรมาจริง ยกผลรันมาให้ดู
2. ค่าที่เทสต์คาดหวัง มาจากไหน — contract ข้อไหน หรือ FR ข้อไหน อ้างมาแบบคำต่อคำ
3. สรุปว่าโค้ดผิด หรือเทสต์ผิด หรือสเปกเองที่กำกวม

ตอบครบสามข้อแล้วหยุด รอให้ฉันตัดสินใจก่อนว่าจะแก้ฝั่งไหน
```

**บังคับให้ AI วินิจฉัยก่อนรักษา** ประโยคสุดท้ายทำให้การตัดสินใจกลับมาอยู่ที่คุณ ซึ่งเป็นที่ที่มันควรอยู่

---

### 🔮 ผลที่คาด

```
1. คาดหวัง: 409 {"error":"duplicate_barcode"}
   ได้จริง:  409 {"error":"duplicate_barcode","details":{"barcode":"8850000000012"}}

2. contracts/products.md เขียนว่า:
   "Response 409: barcode ซ้ำกับสินค้าอื่นที่มีอยู่แล้ว"
   ไม่ได้ระบุรูปแบบ body ไว้ชัด
   แต่ contracts/sales.md เขียนตัวอย่างแบบแบนไว้:
   { "error": "insufficient_stock", "productId": "guid" }

3. สรุป: สเปกกำกวม ไม่ใช่โค้ดผิดหรือเทสต์ผิด
   ตรงกับ R-08 ใน test-plan.md ที่ยังไม่ได้ข้อสรุป
   → เสนอให้ mark Skip อ้าง R-08 ไว้ก่อน รอการตัดสินใจ
```

**นี่คือผลลัพธ์ที่ดี** AI ไม่ได้แก้อะไรเลย แต่บอกได้ว่าปัญหาจริงคืออะไร

## 3.5 เมื่อเทสต์แดงสลับเขียว (flaky)

เทสต์ที่บางครั้งผ่านบางครั้งไม่ผ่าน **อันตรายกว่าเทสต์แดงตลอด** เพราะคนจะเริ่มรันซ้ำจนเขียวแล้วปล่อยผ่าน

```
เทสต์ TC-UI-SALES-015 ผ่านบ้างไม่ผ่านบ้าง รัน 5 รอบแดง 2 รอบ

หาสาเหตุจาก 4 อย่างที่พบบ่อยที่สุดในโปรเจกต์นี้:
1. รอเวลาแบบตายตัว (waitForTimeout) แทนที่จะรอเงื่อนไข
2. ข้อมูลค้างจากเทสต์รอบก่อน โดยเฉพาะสต็อกสินค้าที่ลดลงทุกครั้งที่ checkout
3. เทสต์ตัวอื่นรันขนานแล้วแย่งข้อมูลกัน
4. debounce 250ms ในช่องค้นหา (มีทั้งใน sales/page.tsx และ MemberSearch.tsx)

รันซ้ำ 10 รอบเพื่อยืนยันก่อนสรุป อย่าเดาจากการอ่านโค้ดอย่างเดียว
ห้ามแก้ด้วยการเพิ่ม retry หรือยืดเวลา timeout ให้นานขึ้น
```

**ประโยคสุดท้ายจำเป็น** — `retries: 3` ทำให้เทสต์เขียว แต่บั๊กที่ทำให้มันแดงยังอยู่
และตอนนี้คุณมองไม่เห็นมันแล้ว

## 3.6 อ่านรายงาน Playwright

🔮 เมื่อ E2E พัง Playwright เก็บหลักฐานให้ 3 อย่าง — สอนนักเรียนให้ดูก่อนถาม AI:

| หลักฐาน | บอกอะไร |
|---|---|
| ภาพหน้าจอ ณ วินาทีที่พัง | เห็นเลยว่าหน้าจอค้างตรงไหน มี error dialog อะไรขึ้นไหม |
| trace (`npx playwright show-trace`) | ย้อนดูได้ทีละ action ว่ากดอะไรไปบ้างก่อนพัง |
| network log | เห็น request/response จริงที่ยิงไปหา API |

```bash
npx playwright show-report      # เปิดรายงานในเบราว์เซอร์
```

พอเห็นหลักฐานแล้วค่อยถาม AI จะได้คำตอบตรงกว่ามาก:

```
TC-UI-STOCK-003 แดง ภาพหน้าจอตอนพังแสดงว่า dialog ยังเปิดค้างอยู่
และมีข้อความสีแดงว่า "บาร์โค้ดนี้ถูกใช้กับสินค้าอื่นแล้ว"

network log แสดงว่า POST /api/v1/products ได้ 409

วิเคราะห์ว่าเทสต์นี้ผิดตรงไหน — ตอบก่อน ยังไม่ต้องแก้
```

(คำตอบที่ควรได้: เทสต์ไม่ได้ล้างสินค้าที่สร้างไว้รอบก่อน ทำให้บาร์โค้ดชนตัวเอง —
ตรงกับข้อกำหนด "เทสต์ที่สร้างข้อมูล ต้องลบข้อมูลของตัวเองทิ้ง" ในบทที่ 2)

## วิธีตรวจว่าการรันเชื่อถือได้

- [ ] รันสองรอบติดกันได้ผลเหมือนกัน (ถ้ารอบสองแดง = ข้อมูลไม่ถูกล้าง)
- [ ] จำนวนเทสต์ที่รันตรงกับจำนวนที่คาด (ลดลงเงียบ ๆ = มีเทสต์ถูกลบหรือ skip)
- [ ] `Skipped` ทุกตัวมีเหตุผลกำกับ และมีคนรู้ว่าค้างอยู่
- [ ] เวลารันไม่เพิ่มขึ้นผิดปกติ (Application ต้องอยู่ในหลักมิลลิวินาที)
- [ ] ปิด PostgreSQL แล้วรัน Domain + Application ต้องยังเขียว — **พิสูจน์ constitution ข้อ III**

ข้อสุดท้ายลองได้เลย — สังเกตว่า `dotnet test` รับได้ **ทีละโปรเจกต์เท่านั้น**
ถ้าใส่สองพาธในคำสั่งเดียวจะได้ `MSBUILD : error MSB1008: Only one project can be specified.`

```bash
docker compose stop postgres

cd api
dotnet test tests/TaladPOS.Domain.Tests
dotnet test tests/TaladPOS.Application.Tests

cd .. && docker compose start postgres
```

✅ **ผลจริง** — ทดสอบแล้วขณะ PostgreSQL ถูกปิด:

```
Passed!  - Failed: 0, Passed: 45, Skipped: 0, Total: 45, Duration: 277 ms - TaladPOS.Domain.Tests.dll
Passed!  - Failed: 0, Passed: 39, Skipped: 0, Total: 39, Duration:  40 ms - TaladPOS.Application.Tests.dll
```

ถ้าแดง แปลว่ามีเทสต์แอบพึ่ง database อยู่ ซึ่งผิด constitution ข้อ III

---

## แบบฝึกหัด

**1.** รัน `dotnet test TaladPOS.sln` แล้วบันทึกจำนวนกับเวลาของแต่ละชั้น เทียบกับตัวเลขในบทนี้

**2.** ทำการทดลองปิด PostgreSQL ข้างบน — ยืนยันว่าชั้น 1 กับ 2 ยังเขียว

**3.** แก้เทสต์ที่มีอยู่ 1 ตัวให้แดงโดยตั้งใจ แล้วใช้ prompt ในหัวข้อ 3.4 ถาม AI
ตรวจว่ามันวินิจฉัยก่อนแก้จริงไหม หรือรีบแก้เลย

**4.** สั่ง AI สร้าง `scripts/test-all.sh` ตามหัวข้อ 3.2 แล้วทดลองทำให้ขั้นที่ 3 (`tsc --noEmit`)
ล้มโดยตั้งใจ — ตรวจว่า script หยุดจริงและ exit code ไม่เป็น 0
