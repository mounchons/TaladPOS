# บทที่ 4 — สั่งเพิ่มเทสต์เองภายหลัง

## เป้าหมาย

เพิ่มเทสต์เข้าชุดที่มีอยู่แล้ว โดยไม่ทำของเดิมพัง ไม่เขียนซ้ำ และแผนกับโค้ดยังตรงกันเสมอ

---

## กฎเหล็ก: แผนกับโค้ดต้องเดินไปด้วยกัน

```
        เพิ่มเทสต์               เพิ่มเคสในแผน
             │                         │
             ▼                         ▼
   test-plan.md ไม่ตรงโค้ด      โค้ดไม่มีเทสต์ตามแผน
             │                         │
             └────────► ผิดทั้งคู่ ◄────┘
```

**ทุก prompt ที่เพิ่มเทสต์ ต้องสั่งอัปเดต `test-plan.md` ด้วยเสมอ**
ถ้าไม่ทำ ผ่านไปสามเดือนแผนจะกลายเป็นเอกสารที่โกหก และไม่มีใครกล้าใช้อ้างอิงอีก

---

## 4.1 เพิ่มเคสเดียว

### ✅ Prompt

```
เพิ่มเทสต์ 1 เคส: FR-018 บอกว่าถ้าไม่ระบุ lowStockThreshold ระบบต้องมีค่าเริ่มต้นให้

ทำ 3 อย่างนี้:
1. หาก่อนว่าค่าเริ่มต้นจริง ๆ คือเท่าไร ดูจาก Product.cs และ data-model.md
   ถ้าสองที่ไม่ตรงกัน ให้หยุดแล้วรายงาน อย่าเลือกข้างเอง
2. เพิ่มเคสลงใน test-plan.md หัวข้อ 3 ใช้ ID ที่ยังไม่ถูกใช้
3. เขียนเทสต์จริงใน TaladPOS.Domain.Tests แล้วรันให้ดู
```

**ข้อ 1 คือหัวใจ** — ถ้าไม่บังคับให้ยืนยันค่าก่อน AI จะอ่านจากโค้ดแล้วเขียนเทสต์
ที่ assert ค่านั้น ซึ่งเป็นการล็อกโค้ดปัจจุบันไว้ ไม่ใช่การตรวจสอบตามข้อกำหนด

---

### 🔮 ผลที่คาด

```
พบว่า:
- Product.cs:9  public const int DefaultLowStockThreshold = 5;
  Product.cs:45 SetLowStockThreshold(lowStockThreshold ?? DefaultLowStockThreshold);
- data-model.md:50 เขียนแค่ "มีค่าเริ่มต้นถ้าไม่ได้กำหนด (FR-018)"
  → ไม่ได้ระบุตัวเลขไว้

สรุป: ไม่ขัดกัน แต่เอกสารระบุไม่ครบ
โค้ดเป็นแหล่งเดียวที่บอกว่าค่าคือ 5 → เสนอให้เติมตัวเลขลง data-model.md ด้วย

แก้ไข test-plan.md:
+ | TC-DOM-PROD-005 | ไม่ระบุ lowStockThreshold → ใช้ค่า default 5 | FR-018 | ... | ใหม่ | P2 |
   (เปลี่ยนสถานะจาก "ใหม่" เป็น "มีแล้ว" หลังเขียนเสร็จ)

เพิ่มไฟล์/เมธอด:
  ProductValidationTests.Constructor_WithoutLowStockThreshold_UsesDefaultOfFive()

Passed! - Failed: 0, Passed: 46, Total: 46   (เดิม 45)
```

## 4.2 เพิ่มทั้งกลุ่ม

```
ในแผนหัวข้อ 5.6 (Reports) ยังไม่ได้เขียนโค้ดเลยสักเคส
เขียน TC-API-RPT-001 ถึง TC-API-RPT-005 ให้ครบ

ข้อกำหนด:
- TC-API-RPT-001 (Cashier ได้ 403 ทั้ง 4 endpoint) เขียนเป็น Theory ตัวเดียว
  วนทั้ง 4 path ไม่ต้องแยก 4 เมธอด
- ค่าที่คาดหวังต้องคำนวณจากบิลจริงที่เทสต์สร้างขึ้นเอง
  ไม่ใช่ค่าคงที่ที่เขียนตายตัว เพราะข้อมูลใน database เปลี่ยนได้
- อัปเดตสถานะในแผนจาก "ใหม่" เป็น "มีแล้ว" ให้ครบทุกแถวที่ทำเสร็จ
- รันแล้วรายงานผล
```

**"คำนวณจากบิลจริงที่เทสต์สร้างเอง"** — ถ้าเขียน `totalSalesAmount.Should().Be(12500)` ตายตัว
เทสต์จะแดงทันทีที่มีคนเพิ่มบิลเข้ามา ต้องสร้างบิลเอง แล้วคำนวณผลรวมที่ควรได้ แล้วเทียบ

## 4.3 เพิ่มเทสต์จาก bug ที่เจอ (regression test)

**นี่คือ prompt ที่ควรใช้บ่อยที่สุดในการทำงานจริง** ทุกครั้งที่เจอบั๊ก ต้องมีเทสต์กันไม่ให้กลับมา

### ✅ Prompt

```
เจอบั๊ก: ในหน้าโปรโมชั่น ถ้าร้านมีสินค้าเกิน 100 รายการ
dropdown เลือกสินค้าจะแสดงไม่ครบ ทำให้เลือกสินค้าชิ้นที่ 101 ไม่ได้

ทำตามลำดับนี้ ห้ามสลับ:
1. เขียนเทสต์ที่ทำให้บั๊กนี้ปรากฏก่อน แล้วรันให้เห็นว่ามัน "แดง"
   ถ้าเขียวตั้งแต่แรก แปลว่าเทสต์ยังไม่ได้จับบั๊กจริง ให้แก้เทสต์ก่อน
2. แล้วค่อยแก้โค้ด
3. รันอีกครั้งให้เห็นว่าเขียว
4. เพิ่มเคสนี้ลง test-plan.md พร้อมหมายเหตุว่าเป็น regression test ของบั๊กอะไร

FR ที่เกี่ยวข้องคือ FR-037 อ่านก่อนเริ่ม
```

**ลำดับ "แดงก่อน แล้วค่อยเขียว" ห้ามข้าม** เพราะเป็นวิธีเดียวที่พิสูจน์ได้ว่าเทสต์ตัวนี้
จับบั๊กได้จริง ถ้าเขียนเทสต์หลังแก้โค้ด คุณจะไม่มีวันรู้ว่ามันจับได้จริงหรือแค่บังเอิญเขียว

---

### 🔮 ผลที่คาด

```
ขั้นที่ 1 — เทสต์แดงตามคาด:
  ✗ TC-UI-PROMO-004 dropdown แสดงสินค้าครบทุกชิ้น
    Expected: 137 options
    Received: 100 options
  → ยืนยันว่าเทสต์จับบั๊กได้จริง

ขั้นที่ 2 — วิเคราะห์:
  promotions/page.tsx เรียก searchProducts({}) ซึ่งใช้ fetchAllPages อยู่แล้ว
  ตรวจแล้วพบว่า... [รายละเอียดจริงตอนทำ]

ขั้นที่ 3 — เขียว:
  ✓ TC-UI-PROMO-004 (1.8s)

ขั้นที่ 4 — แผนอัปเดตแล้ว พร้อมหมายเหตุ regression
```

## 4.4 เพิ่มเทสต์หลังแก้โค้ดที่มีอยู่

เมื่อแก้โค้ดเดิม ต้องถามสองคำถาม: เทสต์เดิมยังคุ้มครองอยู่ไหม และต้องเพิ่มอะไร

```
ฉันกำลังจะแก้ DiscountResolver ให้รองรับส่วนลดแบบจำนวนเงินคงที่ (นอกจากเปอร์เซ็นต์)

ก่อนแก้ ตอบก่อน:
1. ตอนนี้มีเทสต์อะไรคุ้มครอง DiscountResolver อยู่บ้าง ลิสต์มาให้ครบ
2. ถ้าแก้ตามที่ว่า เทสต์ตัวไหนจะแดง และแดงเพราะพฤติกรรมเปลี่ยนจริง
   หรือแดงเพราะเทสต์ผูกกับรายละเอียดภายในมากเกินไป
3. ต้องเพิ่มเทสต์ใหม่กี่เคส ครอบคลุมอะไรบ้าง

ยังไม่ต้องแก้อะไร ตอบมาก่อน
```

**ข้อ 2 สอนเรื่องสำคัญ**: เทสต์ที่แดงเพราะ *พฤติกรรมที่ผู้ใช้เห็นเปลี่ยน* คือเทสต์ที่ดี
เทสต์ที่แดงเพราะ *เปลี่ยนชื่อตัวแปรภายใน* คือเทสต์ที่ผูกแน่นเกินไป และควรเขียนใหม่

---

## 4.5 หาว่ายังขาดเทสต์ตรงไหน

```
ไล่ FR-001 ถึง FR-037 ใน spec.md ทีละข้อ แล้วทำตารางรายงาน:

| FR | มีเทสต์ชั้นไหนคุ้มครองบ้าง | รหัส TC | ประเมินความครอบคลุม |

เกณฑ์:
- "ครบ" = มีเทสต์ทั้งทางที่สำเร็จและทางที่ล้มเหลว
- "บางส่วน" = มีแต่ทางที่สำเร็จ
- "ไม่มี" = ไม่มีเทสต์ในชั้นใดเลย

ต้องยืนยันด้วยโค้ดจริงที่มีอยู่ ห้ามนับจาก test-plan.md อย่างเดียว
เพราะแผนอาจระบุว่า "ใหม่" ทั้งที่ยังไม่ได้เขียน

เรียงลำดับให้ "ไม่มี" ขึ้นก่อน
```

**"ห้ามนับจากแผนอย่างเดียว"** สำคัญมาก — แผนบอกว่า *ตั้งใจจะทำอะไร* ส่วนโค้ดบอกว่า *ทำอะไรไปแล้ว*
สองอย่างนี้ต่างกันเสมอ

---

### 🔮 ผลที่คาด

| FR | ชั้นที่คุ้มครอง | รหัส TC | ประเมิน |
|---|---|---|---|
| FR-027 | ไม่มีเลย | — | **ไม่มี** |
| FR-028 | ไม่มีเลย | — | **ไม่มี** |
| FR-018 | Domain (บางส่วน) | TC-DOM-PROD-004 | บางส่วน — ไม่มีเทสต์ค่า default |
| FR-022 | Domain + Application | TC-DOM-DISC-001…006 | ครบ |

## วิธีตรวจว่าเทสต์ที่เพิ่มเข้ามาดีจริง

- [ ] **จำนวนเทสต์เพิ่มขึ้นตามที่คาด** — สั่งเพิ่ม 5 เคส ตัวเลขต้องขยับ 5 พอดี
- [ ] **เทสต์เดิมยังเขียวครบ** — ถ้ามีตัวเดิมแดง ต้องอธิบายได้ว่าทำไม
- [ ] **`test-plan.md` อัปเดตแล้ว** — ทั้ง ID ใหม่และการเปลี่ยนสถานะ "ใหม่" → "มีแล้ว"
- [ ] **ไม่ทับซ้อนของเดิม** — ถามตรง ๆ ว่า *"เคสที่เพิ่งเพิ่ม ต่างจากเทสต์เดิมตัวไหนอย่างไร"*
- [ ] **regression test แดงก่อนแก้โค้ดจริง** — ถ้า AI ข้ามขั้นนี้ ให้สั่งย้อนกลับไปทำใหม่
- [ ] **ไม่มีเทสต์เดิมถูกลบหรือ skip เพิ่ม** — ตรวจด้วย `git diff` ทุกครั้ง

> 🚩 **สัญญาณที่ต้องระวังที่สุด**: จำนวนเทสต์เพิ่มขึ้น แต่จำนวนที่ `Skipped` ก็เพิ่มขึ้นด้วย
> แปลว่า AI เจอเทสต์ที่แดงแล้วเลือกทาง skip แทนที่จะรายงาน ต้องไล่ดูทุกตัวว่าเพราะอะไร

---

## แบบฝึกหัด

**1.** ใช้ prompt หัวข้อ 4.5 หา FR ที่ยังไม่มีเทสต์เลย แล้วเลือกมา 1 ข้อ สั่ง AI เขียนเทสต์ให้ครบ

**2.** จำลองบั๊กขึ้นมา 1 ตัว โดยแก้โค้ดใน `api/src/` ให้ผิด แล้วใช้ prompt หัวข้อ 4.3
บังคับให้ AI ทำครบ 4 ขั้น ตรวจว่ามันเขียนเทสต์แดงก่อนจริงไหม

**3.** สั่ง AI เพิ่มเทสต์ 3 เคส **โดยตั้งใจไม่บอกให้อัปเดต `test-plan.md`** แล้วดูว่ามันอัปเดตเองไหม
บันทึกผล — นี่คือเหตุผลที่ต้องเขียนข้อกำหนดนี้ลงไปในทุก prompt

**4.** (ยาก) เขียน prompt ให้ AI ตรวจหา **เทสต์ที่ไม่ได้ตรวจอะไรจริง** ในชุดที่มีอยู่ 93 ตัว
คำใบ้: มองหาเทสต์ที่ assert แค่ `NotBeNull()` หรือเทสต์ที่ยังเขียวแม้ลบ logic ในโค้ดออก
